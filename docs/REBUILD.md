# 从零重建与分支规则

## 本轮范围

只整理 Rho-core。Rho 与 Rho-plugins 的源码、主分支、公共依赖和应用组合暂时不动。
这次交付是设计与源码基线切换；新的可执行 Core 在后续里程碑中建立。目标是补足
实际受管执行缺口；Agent 使用已有工具的路径与可选协议接入层都在 Core 边界之外。

| 分支 | 用途 |
| --- | --- |
| `codex/legacy-core-before-rebuild` | 固定保留重建前的完整受控源码、测试、生成依赖、原文档与本地已提交改动 |
| `main` | 新设计文档、工作规则、许可证与政策；后续新源码的开发位置 |

归档以重建前本地 HEAD 建立，不从远程旧头重建。它保留 Git 中的源码和历史，
不包含未受控构建缓存、运行目录或用户数据，也不是官方制品或已发布版本。
归档分支不继续承担新架构开发，不将它合并回 `main` 来恢复旧子系统。

主分支移除旧 `crates/`、`sdk/`、构建脚本、Cargo 配置与职责搬迁文档。
原文件可在归档分支查看。许可证和仓库元数据保留；安全与隐私说明改为新实现的
明确要求，不继续描述旧运行时为当前功能。用户审核报告作为设计输入保存在主分支。

## 查看旧材料

```sh
git show codex/legacy-core-before-rebuild:docs/MISSION-AND-PLAN.md
git show codex/legacy-core-before-rebuild:Cargo.toml
git ls-tree --name-only codex/legacy-core-before-rebuild
```

只有一个具体用户需求或故障需要对照时才读取旧源码。需要独立运行历史代码时，
另行选定临时工作树和临时项目，不将主分支切回旧代码，不使用用户正在运行的 Host。
归档中旧测试的通过情况不构成新契约的验收。

## 新实现的工作顺序

1. 在 `main` 读取使命、架构与审核取舍，选择一个有明确完成条件的调用方动作。
2. 先用已有工具验证，说明它无法提供的受管保证，再建立必要源码、契约和定向验证；
   不以统一目录、协议框架或逐方法入口为起点，语言及依赖通过实际需要选定。
3. 使用新临时项目和存储，独立构建与验收；不要求兼容原 SDK、目录、包格式和数据库。
4. 检查 diff，更新确实变化的设计决策，提交连贯改动；区分已设计、已实现和已验证。
5. 协议接入、SDK 导出与跨仓集成按实际消费者单独选定，不是固定交付终点。
   需要导出时保持必要契约的单一源头；跨仓消费者与组件组合仅在该集成范围内修改。

Core 夹具只验证对象、执行与回报事实，不能代替真实科学结果。外部工具的动作不
要求登记到 Core；受管保证必须说明覆盖的动作、进程寿命与保留期限。客户端接入
与原生适配可同仓同进程存在，但 Core 不反向依赖协议类型或客户端特性。

主分支暂时没有 Cargo 项目或公共 SDK，不应运行原构建、原生成脚本或应用协调器
来验证新 Core。磁盘上可能仍有忽略的旧 `target/` 或缓存；它们不是新源码、新构建
或新验收证据。文档阶段运行链接与渲染检查，不以旧二进制补足不存在的新实现。

## 发布与范围控制

分支建立和本地提交不等于推送。后续获授权发布时，先核对实际 remote、分支和账户，
先保全归档分支，再推送新主分支，最后核对远程头。不重写既有 Git 历史，不强推，
不顺带合并 PR、发布二进制或更换用户安装。历史分支的源码仍可查阅。

应用现有文档与组合可能继续引用旧 Core；这是本次单仓范围的已知边界，不以兼容层、
SDK 偷改或自动更新锁文件补齐。真正的产品可用性由后续选定组合的真实用户流程证明。
