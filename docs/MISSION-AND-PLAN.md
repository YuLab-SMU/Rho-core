# Rho Core：从零重建的使命与实施计划

设计基线：2026-10-10。本文件规定目标和验收，不描述已有新功能。职责、依赖方向与
执行保证见 [Architecture](ARCHITECTURE.md)，审核依据见
[Audit decisions](AUDIT-DECISIONS.md)，源码状态见 [README](../README.md)。

## 从 Agent 的实际工作出发

研究者提出问题；外部 Agent 在已有环境中阅读材料与工具文档，选择方法，编写脚本，
组合 CLI、SDK、MCP 或原生运行能力，再依据真实反馈继续。调用方可以换模型、
改变计划或尝试新方法，无需先向 Core 增加对应的科研操作。

Core 的使命是补足这段工作中有证据的执行缺口：明确定位受管对象、持有需要持续的
动作、保护约定范围的重复送达、找回回报。已有工具能独立完成的工作继续使用原工具。
这不是“所有能力先接入 Rho”的集成计划，也不是另建一个 Agent harness。

此次从零重建不受旧 crate、OperationGateway、QuerySnapshot、catalog、SDK 类型、
包协议与职责搬迁路线约束。旧代码只用于回答具体需求或故障问题，不能以历史测试
或沉没成本为理由保留子系统。Rho 与 Rho-plugins 本轮不变。

## 责任与选择路径

| 参与方 | 承担的责任 | 何时需要新增实现 |
| --- | --- | --- |
| 外部 Agent 或普通调用方 | 目的、文档读取、工具选择、代码组合、上下文和停止策略 | 现有调用环境缺少真实任务需要的能力时，由该环境的 Owner 解决 |
| Core | 自己的程序调用边界、所选受管动作与必要回报接续 | 原工具无法满足明确对象、执行寿命或受理保护需要时 |
| 原生执行方与领域 Owner | 真实对象、语言状态、原生执行条件、读写、结果与局部恢复 | 原生语义出现具体缺口时；不把每种分析方法翻译成 Rho 工具 |
| 可选接入层与应用装配 | 客户端协议、部署、认证、界面和组件选择 | 实际消费者需要某种接入时；接入层依赖 Core，反向依赖禁止 |
| 研究者 | 问题与方法取舍、解释、复核及科研主张 | 执行回报不能替代科学判断 |

Skills 是可读的调用指导，Loop 属于调用方的反馈循环，Graph 可由调用方按用途
组织关系；都不要求 Core 建设加载器、循环引擎或图存储。按需文档、类型、示例与
可用的结果入口是接口质量，不要求统一工具目录、搜索引擎或全量上下文注入。

| 实际动作 | 优先实现方式 | 必须可观察的结果 |
| --- | --- | --- |
| 读取材料、搜索或编辑脚本 | 已有文件、编辑与 Git 工具 | 真实内容、明确范围与实际写入保证；新状态不能冒充旧输入 |
| 新方法或新的外部服务 | 原文档、原 CLI/SDK/MCP、Agent 编写的代码 | 不改 Core 也能组合和检查反馈；直接动作的保证由实际工具提供 |
| 需要持有的原生任务或会话动作 | 对选定 Owner 的最小受管调用 | 对象关联、实际请求、执行身份与结果入口；Owner 判断原生条件 |
| 等待丢失后继续 | 读取原受理与已有原生任务 | 找回同一执行或明确未知；不自动重跑 |
| 中止或结束受管工作 | 原生取消与结果观察 | 取消请求、停止确认和资源释放分别表达；断线不等于停止 |

核心只对自己受理且声明保护的动作负责。外部工具的修改可再次观察，不能自动登记
成 Core 已管理的执行，也不能承诺它们具有 Rho 的去重、历史或接续保证。首版是
可信单用户本地流程；已授权工作只做必要的机械与原生检查，不增加 Rho 审批。

## 选择结构前先证明价值

| 问题 | 初始选择 | 增加机制所需的证据 |
| --- | --- | --- |
| 怎样接入 Core | 一个实际调用方使用独立程序边界 | 某个真实客户端确需协议入口；只在外层增加该适配 |
| 怎样获得外部能力 | 直接使用原工具与文档 | 原工具缺少选定受管保证；统一命名或目录整齐不是理由 |
| 怎样支持新科研方法 | 在已有环境中编写与运行代码 | 重复的真实任务表明领域专用工具有可测量收益；由实际 Owner 提供 |
| 怎样持续执行与接续 | 复用原生句柄、查询和持有机制 | 原机制存在可复现缺口，再补最小关联与记录 |
| 怎样保存事实 | 为声明的接续和去重需要选择成熟存储 | 故障实验暴露持久化或容量问题；不默认保留每次读取和所有中间数据 |
| 怎样隔离和限制代码 | 复用实际执行环境的控制 | 选定部署确需额外隔离时，由该边界的 Owner 实施和验证 |
| 怎样选择专用工具或代码组合 | 在同一真实任务中比较 | 完成质量、调用成本、上下文使用和维护负担可解释；不预设唯一范式 |

首个路径可以是普通模块与函数，接入层可以同进程存在。需要共享的机制以实际缺口
为依据，既不预建通用框架，也不要求凑足两个流程才修复已证明的问题。语言、库和
版本通过实施中的小实验选择；框架流行、可扩展性或“agentic”标签不构成选型证据。

## 不能交给模型猜测的事实

- 原生对象是否还是原对象、是否忙碌、是否满足写入或执行条件，由实际 Owner 在操作处判断。
- 模型上下文不能证明真实世界未改变；当前观察不能补造历史来源或动作因果。
- 受理、原生副作用和回报保存并非天然事务；不宣称外部 exactly-once，不因未知重新派发。
- 同一请求重复送达与有意再次执行区分身份。调用方代持身份，保留期限和进程寿命范围公开说明。
- 取消请求、取消确认、任务结束、资源释放与回滚不同；结果未知只限制实际依赖的后续动作。
- 代码组合不产生跨调用事务。部分脚本已经执行时，重跑整段代码可能重复副作用。
- 直接外部调用服从其环境与原生工具的权限和限制。Core 的记录与锁不能约束所有外部动作。

这些事实约束所选行为，不要求复建通用状态机、恢复引擎、全局版本、世界模型、
向量记忆或科研证据账本。原生能力已经满足某个保证时，应复用而非再包装一层。

## 分阶段实施与完成条件

| 阶段 | 有界交付 | 通过条件 |
| --- | --- | --- |
| 0：设计基线 | 归档旧源码，定义 Agent 工作方式与 Core 边界 | `main` 保留设计、政策与元数据；旧受控源码完整归档；其他仓库不变 |
| 1：首个受管流程 | 普通程序调用一个选定执行方；最小对象关联、请求身份、执行持有与结果读取 | 临时项目中执行真实夹具任务；结束一个等待者后另一个能读取原执行；同身份不重复派发；冲突身份与错误对象拒绝；两个不同任务脚本复用同一能力，不增加方法入口 |
| 2：所需故障接续 | 对首个流程声明的持久化、重启、取消与输出限制补足保证 | 受理保存失败不派发；崩溃后查询已有任务或明确未知，不自动重跑；回报保存失败与原生完成分别表达；停止未经确认不能报成功；过期与容量行为可验证 |
| 按需：客户端接入 | 实际消费者需要的一种可选接入方式 | 协议差异留在外层；直接调用与该入口都守住同一受管约束；不逐科研能力写入口，不依赖客户端特性改变 Core |
| 另行选定：领域与产品集成 | 一个真实 Owner 与对应消费者 | 使用真实会话、数据和产物验收；选定必要公共依赖与组件；夹具结果不能代替科学或产品通过 |

阶段 1 先明确仅在进程寿命内成立的保证；需要跨重启的能力在阶段 2 通过后才能
声称成立。夹具可以持有真实本地任务并产生可检查的输出，不能伪造 R 或科学结果。
普通文件读取由已有工具完成，不再把建设一套文件入口作为 Core 的起点。

协议入口、领域接入协议和独立 SDK 均不是固定阶段终点。已有程序边界与原生接口
够用时即可交付；真实消费者需要导出时只维护必要契约。包安装、热重载、依赖解析、
视图协议和插件商城不进入首个受管流程。分期用于形成可验收的增量，不要求全产品
或所有失败恢复机制先完成才能使用已经明确范围的能力。

## 验证与完成规则

每项任务先写调用方动作、已有工具的实测结果、Core 补足的具体缺口、成功回报和
一个实际失败。验收检查对象、字节、派发次数、原请求与结果，不检查旧目录形状。
对受理、派发与保存结果的中断用定向故障实验，不建立先于功能的通用评估平台。

Core 独立构建和验收，不依赖相邻源码；使用最小原生执行夹具，不把外部模型、
Files 或 R 集成作为单仓前置。接口可用性由实际调用方检验；Agent 评估在具备真实
调用环境时选定，用文档和现有工具闭合任务，不为评估在 Core 内嵌模型循环。

每个资源限额说明保护的资源、默认值、配置与超限行为。Core 只为自己拥有的资源
负责；不默认无限缓存、排队或输出，也不建一个监控全环境的配额系统。普通读取
不记账，中间数据不强制传回模型。正确性条件逐个满足，性能与成本目标来自选定
任务的实测，不采用报告中无依据的统一百分比门槛。

每次扩张检查：换客户端、换模型、增加方法是否必须改 Core；能否直接复用已有能力；
所增机制的实际保证与成本是什么。阶段结束分别报告已设计、已实现与已验证的范围。
单仓闭合不顺带刷新其他仓库 SDK、应用锁或旧消费者，也不增加兼容层。
