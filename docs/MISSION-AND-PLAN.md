## 使命与需要纠正的问题

Rho 应帮助研究者和外部 Agent 从不完整、持续变化的计算现场出发，读取真实材料、
开展分析、检查结果，并逐步提高对关键结论的把握。来源不全、外部修改、缓存、
局部失败和相互冲突的描述都是正常工作条件。

需要纠正的是：将受管操作的可靠性协议扩大为普通工作的通行条件，要求用户先维护
一套完整的身份、版本、确认和来源关系，才能继续研究。记录一致不能证明现实完整，
执行成功不能证明分析正确，职责搬到插件也不能自动减少用户负担。

判断改进是否有价值，应看它是否让一项真实工作更容易完成，以及是否避免具体损失。
代码行数、状态标签数量、测试数量和抽象的通用性不能代替这个判断。

已经收敛的原则：

- 记录要诚实，认识可以修正；已引用的原始请求、观察或评估不被新材料静默替换。
- 观察优先，版本按需保留，关系显式声明，受管动作最小记账。
- 上下文围绕当前问题取得；材料未齐不成为普通工作必须等待的统一条件。
- 底层判断明确契约和原生条件；科研意义、是否值得重跑及主张是否充分由上层判断。
- 权限体系建设后置；先完成本地科研工作流，不以权限配置或审批作为基础能力的前置任务。
- 继续工作的条件由下一步动作的后果和必要前提决定，不由全项目证据是否完美决定。
- 未知连同观察范围传递；上层判断它影响哪个用途，并选择比较、另存或建立新分析基线。
- 成熟编辑器、文件、Git 和维护中的工具优先复用；新增机制必须有已证明的共同缺口。
- 查询、记录保留、关系解释和科学论证分别拥有自己的责任，不把它们贯通成审批流水线。

## 支持智能判断的工作环境

Rho 所服务的智能，是研究者或 Agent 在不完全可观察、持续变化的环境中，利用已有
材料形成判断、采取具体行动、观察反馈并修正认识，以持续推进目标的能力。这是
本项目的设计取向，不是对所有智能的学术定义，也不据此添加新的运行时框架。

近期 Core 的能力围绕取得材料、实施明确动作、找回必要回报选题。研究者和 Agent
可以从当前问题出发，观察、比较、解释、行动和重新评估，无需按固定工作流逐级通关。

| 参与方 | 对什么负责 |
| --- | --- |
| Core | 传递请求和回报，定位已有受理记录，维护自己承担的记录与执行约束；描述自身已知的处理情况 |
| 领域 Owner | 接触真实对象，报告这次观察和执行回报及其范围；提供具体原生能力和条件 |
| Agent 与领域工具 | 按问题取得材料，结合目标、假设和历史解释意义，选择下一步并修正判断 |
| 研究者 | 决定目的与取舍，审阅或修正解释，保留使用其他工具和继续工作的选择 |

Core 不拥有外部世界的事实真值，也不建立稳定完整的世界模型。Owner 的回报仍有
观察范围和限制；请求中声明的输入、实际观察到的材料、原生执行回报和推断分别表达。
上下文可以不足，解释可以冲突。不得用“Core 管事实”把受理记录升级为外部历史，
也不得将“底层不替 Agent 判断”解释成取消必要的对象定位和原生执行检查。

区分三类决定：具体动作不可违反的条件由实际 Owner 或 Core 检查，例如身份不匹配、
过期内容覆盖或原生会话正在执行；项目权限与确认策略待场景明确后设计；材料是否有
科研价值、是否需要重算以及主张是否充分，由研究者、Agent 或领域方法解释。
这用于分清责任，不新增三套约束模型；原生文件版本的判断仍属于 Files 等真实 Owner。

可修正性通过保留确有用途的依据、呈现新观察和允许更新解释来支持。普通笔记、当前
索引和探索性判断仍可编辑，不为每一次认识变化预建 revision infrastructure 或另建
不可变账本。证据和反例围绕具体主张使用，不形成对象固有的可靠性分数。

## 权限体系建设后置

近期先让研究者在自己选择的本地项目中读取、编辑、运行和检查结果。普通工作不新增
用户、角色、逐能力授权配置或审批步骤，也不为未来可能的部署场景预建权限框架。
当多用户共享、远程访问或实际权限隔离成为选定需求时，再按明确的使用场景设计。

目标定位、并发写入检查、原生会话的实际忙碌条件以及避免重复执行，分别保护具体对象
和工作成果。这些检查按真实动作保留，不借此扩展成统一的权限或风险门控体系。
Core 近期图示中的查询通道应表达路由和有界通信，操作通道应表达执行协调与最小记账。

当前代码中的 launcher grants 等权限机制仍是实现事实，见 Architecture；它们不规定
后续工作必须先建设权限体系。在选定本地流程中若造成额外配置或阻断，应在实际所属
边界单独简化。本次调整计划与实施顺序，不宣称已有权限代码已经移除。

## 分层：观察不是关系，关系不是证据，证据不是结论

下面是概念层次，不是新的 Core 类型目录或必须逐层升级的产品流程。

| 层次 | 回答的问题 | 主要责任 | 不能自动推出 |
| --- | --- | --- | --- |
| 现实对象 | 实际接触什么？ | 文件、原生会话、进程、远程任务及其 Owner | Rho 掌握对象的全部历史 |
| 观察结果 | 这次在什么范围、时间、方式下看到了什么？ | Owner 的有界 Query；Core 保持通用通信与限定 | 过去一直如此，或由哪个操作造成 |
| 记录与保留版本 | 哪些材料需要以后引用、比较或恢复？ | 当前用途的 Owner 按需接纳；复用资源和存储 | 两份记录有因果关系 |
| 关系视图 | 这些材料在某个用途下如何关联？ | 插件或上层按规则构造局部投影 | 候选关系已经验证 |
| 证据结构 | 某份材料如何支持、挑战或限定一项主张？ | 针对 Claim 的领域工具或研究者 | 主张已经成立 |
| 论证与决策 | 在哪些假设与适用范围内可以判断或行动？ | 领域方法、研究者及其选择的调用方 | 判断适用于未检查的条件 |

每一层都可以独立存在。有观察可以无需建图；有关系可以没有 Claim；有材料可以
无法回答某项主张；有论证也可以仅适用于有限条件。这些情况不应被当成系统失败。

图是有目的、有输入、有生成规则的投影，不是全局底账。以后确需生成图时，保留
输入记录、生成者、时间、范围和规则版本，允许不同视角和互相冲突的解释同时存在。

证据是材料在特定 Claim 和使用范围中的角色。不得给文件或项目附加一个固有的
“可信度”，再用它替代具体检查。原生回执、用户声明、规则推断、Agent 建议和复核支持
需要保留各自依据，不能静默升级或将矛盾平均成一个分数。

## Core 保留什么，按需能力放在哪里

Core 近期对自己的受理、路由、执行协调和记账负责；领域 Owner 对原生语义、
状态观察、前置条件和恢复解释负责；科研关系、证据和论证由更上层按用途组织。

| 责任 | Core 边界 | 所属 Owner 或上层边界 |
| --- | --- | --- |
| 读取观察 | 明确项目、对象与 Provider，提供有界通信；保留时间、完整性和限制说明 | 实际读取、原生身份、分页、缓存及是否能观察 |
| 受管副作用 | 原请求、明确请求标识的重复送达保护、执行协调和必要回报 | 实际影响、原生前置条件、部分结果及具体控制能力 |
| 记录与版本保留 | 复用已有通用资源和 Operation；共同缺口证明后才新增最小机制 | 决定哪些观察值得保存、是否保留字节、用途和保留策略 |
| 编辑与冲突 | 不恢复通用草稿、编辑历史或工作台内容模型 | Editor、Studio 与 Files 各自承担缓冲区和真实文件责任 |
| 关系、证据和论证 | 不建立可信度内核、科学真相图或项目评分 | 局部投影、Claim、依据、假设、反例与重新评估 |
| 下一步动作约束 | 明确用户请求、目标与实际执行边界；普通工作不新增权限配置或审批 | 该动作所需的原生条件、领域检查和安全替代路径 |

讨论中的 `Context Envelope`、`Observer`、`Recorder`、`Version Manager`、`Projector` 和 `Action Gate`
描述不同责任，属于候选设计词汇，不能仅凭命名就新增服务、数据库、枚举或 Rust 接口。
尤其不预先将 Recorder 与 Version Manager 固化进 Core；先用真实 Owner 流程判断
现有文件、资源、Git 和 Operation 是否已经足够。多个真实流程缺少相同语义时，
才讨论最小公共部分。

将工程检查下沉到 Owner，不意味着增加另一份科学操作账本。将内容与布局移出 Core，
也不意味着逐字重建原来的状态机。必须重新判断用户行为实际需要的机制。

Context View 指调用方围绕当前问题组织的有限上下文，不是 Core 模块、固定对象或
必经入口。优先使用 Owner 已有查询、真实文件、原生日志和任务句柄，按需发现、逐步
读取并组合。历史、输入版本、环境、变化和副作用都是可能有用的材料；不要求每次
执行前齐备，也不保证捕获全部动态输入。恰当的观察范围比尽可能多的上下文更有用。

对已有引用的预览应验证原身份与版本，不静默替换成当前字节。引用已变化时，返回
具体限制并提供重新观察的入口；新观察作为新材料使用，不冒充原引用。不同 Owner
的查询时点和范围分别保留，不把组合结果包装成全项目原子快照。

能力目录说明有哪些入口、需要哪些具体参数和原生条件，不生成一个经全局风险判断
批准的动作集合。科学上的适用性由研究者、Agent 或领域方法判断。文件可读、接口
可调用或返回值符合 schema，各自只说明对应边界，不能自动推出结果有效或值得重跑。

## Core 的信息与行为设计：Skill、Loop、Graph

Skills、Loop 和 Graph 不是 Core 外面的一层适配，也不是三个需要独立部署的产品模块。
它们是 Core 设计已有信息和行为时的三个正交视角：Skill 让一个信息模块可理解、可
渐进披露；Loop 让研究者或 Agent 能从一次观察继续到下一步行动；Graph 让明确的记录
关系可以被定位、组合和局部导航。大多数 Agent 已经能够消费这些形式，Core 要做的是
让自己的信息和状态天然适合这种工作，而不是再造一个 Agent 运行时。

### 1. Skill：每个信息模块都有自己的可理解接口

Skill 的思想应融入能力发现、观察、Operation、记录、资源和生命周期等信息模块。
它不是 Core 执行 `SKILL.md` 的加载器，也不是每次调用都必须经过的 SOP。一个模块
可以按照当前问题只暴露最少信息，需要时再展开；同一份底层事实不能因为披露层次不同
而变成不同版本。

| 信息模块 | 先披露什么 | 需要时展开什么 | 仍由谁判断 |
| --- | --- | --- | --- |
| 能力发现 | 用途、Owner、可读/可执行类型、简短限制 | 参数 schema、前置条件、影响、重试/取消、示例和相关入口 | 是否选择这项能力以及科学适用性 |
| 观察与上下文 | 对象、来源、观察范围、当前状态 | 时间、完整性、缓存/部分结果、限制说明、引用预览和 `next_reads` | 这次材料是否足以回答问题 |
| Operation 与动作 | 目标、动作类型、当前状态和是否已有记录 | 原请求、规范参数、前置条件、执行回报、错误、恢复材料和取消情况 | 是否继续、另行分析或有意重跑 |
| 记录与事件 | 可见范围、记录类型、最近变化 | `OperationId`、请求 ID、事件游标、原始回报和明确关联 | 哪些记录值得长期保留、怎样解释 |
| 资源、实例与连接 | 身份、可用性、用途 | 原生版本、能力限制、资源引用、连接条件和关闭要求 | 是否使用、切换或释放资源 |

因此，现有 `CapabilityDocumentation`、`QuerySnapshot`、`ContextReference`、
`OperationRecord`、`NextRead` 和事件游标不是彼此孤立的字段；它们是不同模块的
Skill-shaped 信息。`overview`、`catalog`、`describe` 是可用的披露视图，不构成固定
顺序。已知能力可以直接调用，低层材料也可以先于说明被读取。

### 2. Loop：Core 管理可观察的行为边界

Loop 关注人在不完整现实中怎样持续工作，而不是模型如何生成 prompt。一个可继续的
行为通常包含：提出问题或意图、取得有限观察、选择明确动作、收到反馈、判断缺口，
然后继续、分支、暂停或结束。它不要求每次严格按这个顺序，也不把普通阅读变成
Operation。Loop 对 Core 的启发不只是“外部 Agent 能不能调用”，而是 Core 需要管理
这些行为与现实接触时可被观察、可被定位、可被安全继续的边界。

Core 要为这个循环保留和暴露足够的连接点：

- Query 返回观察范围、完整性、限制和下一项读取入口，不创建虚假的完成状态。
- Operation 保留原请求、`client_request_id`、`OperationId`、目标、前置条件、当前状态、
  回报和不确定性，让调用方能找回一次动作而不是猜测它是否发生。
- `next_reads`、事件游标、取消请求、原生句柄和 `reconcile_commit` 提供具体的继续
  动作；它们不合并成通用的“恢复中”状态机。
- 连接丢失、回报未知或外部文件变化只改变可观察材料，不自动替调用方决定重跑、
  回滚或结束研究。

因此，Core 可以管理以下行为边界：谁在当前调用上下文中行动、已选能力如何路由、
请求是否受理、一次受管动作何时受理和结束、任务在连接丢失后是否仍归 Host 所有、取消或提交恢复针对
哪个原动作，以及下一步可读取哪些材料。Core 不管理以下认知内容：目的、计划、
消息历史、分支选择、停止条件、协作规则和科学解释。研究者和 Agent 都可以使用同一
套边界；Core 不把“人”和“Agent”强行拆成两套行为模型。

### 3. Graph：显式关系支持行为管理与导航

Graph 的价值首先是帮助人或 Agent 管理和定位行为：找到“这项观察来自哪里、影响了
哪个动作、下一步还能读什么、哪个分支仍然开放”，而不是在 Core 内建立科学世界图。
Core 已有的 `operation_id`、
`client_request_id`、`correlation_id`、`causation_id`、`ContextReference`、事件序号、
原生对象身份和 `next_reads`，可以作为局部行为图的节点标识和声明关系。

这些关系必须标明来源和范围：

- `causation_id` 表达一次请求声明的直接触发来源，不证明科学因果，也不包含所有输入。
- `correlation_id` 表达调用方希望一起追踪的记录，不证明它们共享同一现实状态。
- 事件序号表达 Journal 中的可见顺序，不是科研对象的全局版本号。
- `ContextReference` 表达 Owner 定义的原生定位，不能被当成 Core 已经保存的内容。
- `next_reads` 表达一个记录建议的读取入口，不等于已经存在的依赖边或执行计划。

外部运行时可以据此生成一个当前问题所需的局部行为图，并用它管理分支、交接、暂停
和继续，再与 Claim、证据、假设和反例叠加。Core 可在确有导航缺口时提供有范围、有
分页的关系读取；不预建全局 DAG、图调度器、Reducer、checkpoint 或自动因果邻域。
图是行为管理的视角和投影，不是新的项目主数据。

### 行为管理的责任分界

| 行为管理问题 | Core 可以保留和约束什么 | 人或 Agent 仍然决定什么 |
| --- | --- | --- |
| 谁在行动、在哪个交互中行动 | `caller`、`principal`、项目范围、`connection_id` 和可见性 | 参与者的目标、角色意义和协作方式 |
| 当前正在做什么 | 能力、目标、原请求、Operation 状态、原生句柄和已知回报 | 这项动作服务于哪个问题，是否值得继续 |
| 观察改变了什么 | Query 的时间、范围、完整性、限制和 `next_reads` | 这条观察是否改变假设、证据或下一步选择 |
| 哪些行为彼此相关 | 明确的 correlation、causation、事件顺序和 Owner 引用 | 将关系组成何种局部图、是否作为工作分支或论证依据 |
| 中断后怎样继续 | 原记录、事件游标、取消状态、保留回报和具体恢复入口 | 继续观察、暂停、切换路径、另行执行或结束 |

这使 Core 成为行为的可观察边界和协调底座，而不是行为的决策者。只有当一个具体
流程需要跨记录定位、分支恢复或多人/多 Agent 协作时，才增加最小的关系读取或继续
材料；不因 Graph 或 Loop 的概念存在就预建统一行为状态机。

### 三种视角如何共同落到 Core

同一项工作可以同时出现于三个视角，但不需要三套状态：

| Core 信息 | Skill 视角 | Loop 视角 | Graph 视角 |
| --- | --- | --- | --- |
| 能力描述 | 先说明用途，再按需展开契约 | 为下一次观察或动作提供入口 | 与相关能力和前置读取相连 |
| QuerySnapshot | 说明观察范围、完整性和限制 | 决定继续读取、比较或行动 | 连接到被观察对象和后续记录 |
| OperationRecord | 说明动作、前置条件和回报 | 从受理到结果未知、结算或继续观察 | 连接请求、触发来源、事件和原生对象 |
| ContextReference | 说明如何定位和预览材料 | 支持从当前问题继续取材 | 连接 Owner、对象、版本/摘要和引用 |
| 事件与 `next_reads` | 说明还有哪些相关材料 | 暴露可执行的下一步 | 形成局部分支和返回路径 |

“发现、观察、行动、关联、继续”仍是调用方常见的五种行为，但现在它们被落实为
信息模块的披露方式、Core 管理的行为边界、Loop 的继续连接点和 Graph 的显式关系，
而不是五种新服务或一次性的 Agent 兼容性测试。现有入口与代码位置见
[Architecture](ARCHITECTURE.md#agent-facing-entry-points)。

Plans、messages、todo、模型上下文、图状态和 checkpoint 仍属于外部运行时；它们可以
引用 Rho 材料，却不能成为项目现实的主数据。Core 只保留自己需要承担的关系、事件和
继续工作信息。权限体系继续后置，关系查询继续以具体导航缺口为前提。

## 观察、记录与保留策略

一次查询返回观察结果，不因此建立长期记录。Core 的查询网关不创建 Operation；
一次读取不应要求新增项目写入租约或恢复原操作。现有 Host 的租约仍承担它自己的
协调责任，Owner 对实际忙碌和原生访问条件作自己的限定。
未知观察时间保持未知，回复时间不能冒充原生观察时间，缓存不能冒充刚刚检查。

文件 watcher、进程通知和调度器回调可以提示重新观察。提示本身不能证明外部编辑、
执行完成或因果关系；不将每条通知、轮询、按钮点击或内部函数调用持久化为科研事件。

以 A、B 两次文件观察为例：可以记录内容不同，不能据此补造修改者、修改时间、
编辑工具或中间版本。相同字节也不一定是同一个原生文件，内容身份与原生身份按用途区分。

| 材料 | 默认处理方向 | 需要说明的边界 |
| --- | --- | --- |
| 变化提示、重复轮询、临时交互 | 合并、去抖、丢弃或短期诊断 | 不承担长期来源证明；不承诺捕获所有变化 |
| 当前目录、元数据与摘要索引 | 可更新、可重建 | 当前索引不替代历史观察 |
| 操作前检查、活跃输入选择、冲突发现 | 依据用途选择持久保留 | 记录主体、观察范围、时间、来源与限制 |
| 为比较、草稿恢复或选定结果复核所需的字节 | 按该用途保留确切版本 | 不要求每次探索冻结全部输入与环境；摘要或路径本身不能恢复源字节 |
| 原生回执、复核结果与重要用途决定 | 按项目与 Owner 策略保留 | 保留与原请求或明确主张的关联，不解释为科学结论 |
| 内部 trace、性能日志 | 采样、限期、与科研材料分开 | 不用无限诊断记录弥补科学记录缺口 |

相同内容可以复用保留版本，普通重复读取可以只更新当前索引；但新的关键检查可能
有独立的时间与决策意义，不能为去重而抹掉它。原观察时间不改写，`last_seen` 不冒充
重新验证的完整证明。不同 Owner 的先后读取不组成原子快照。
“未检测到变化”只描述检测范围内的结果；差异行号不重叠也不能证明合并后的科学意义
不变。Agent 可以据此比较或尝试合并，具体写入仍处理它自己的内容与并发条件。

只有选定保留的材料承担历史引用责任。普通重复观察不要求累积入库；重要解释若需
替换旧解释，可以引用旧依据和新反例，不强制每个 Claim 使用统一 supersedes 状态机。

这是保留策略方向，不宣称现有 catalog 已实现上述存储。具体机制和限额在选定流程
中确定，说明保护的资源、配置方式、超限行为和引用材料的保护方式。不能以静默截断
代替完整材料，也不能默认永久保存全部观察或立即建设一个通用 Observation Store。

## Operation 与继续工作的边界

Operation 是 Rho 自身受管副作用的控制记录，不是重建整个外部世界的主数据模型。
保留必要的调用者、项目、原请求、目标、前置条件、执行回报和最终结算；
内部 trace 不进入它的科研语义。已有生命周期事件或 outbox 不能仅因含有“事件”
就删除，也不能据此将系统解释为全局 Event Sourcing。逐项依据实际作用决定取舍。

科研计算可以随机、状态化或具有不可重复的副作用。当前契约中的“幂等”限定为调用方
明确提供的请求标识在其记录范围内重复送达时定位原受理记录；Core 不根据代码相同、
时间接近或动作相似度推断科研意图。明确再跑一次使用新的请求标识。客户端应代为持有
标识，不要求研究者手工管理它；标识丢失或原生关联未知时，不承诺可还原整个过程。

原生执行、账本提交与结果送达分别表达。禁止因丢失回报自动重跑原动作，也不能将
取消请求、连接结束或视图关闭解释为执行停止或回滚。提交恢复只结算保留的原候选结果，
不重建未知外部历史。

恢复必须说明具体动作：重新连接已有任务、读取日志、补存保留回报和重新执行代码
分别处理。Owner 有原生句柄或维护中的工具时优先复用；未知结果不推导出通用的
“可恢复”状态或自动续跑。Core 的提交恢复只处理自己的保留回报，不承担统一科研恢复。
是否重跑和重跑的科研意义由研究者或 Agent 判断，新的执行仍满足真实原生条件。

`Uncertain` 可以结束一次执行尝试，但不结束后续认识。后续观察和复核可以增加材料，
原身份和历史记录不被覆盖。分别回答三个问题：

1. 旧动作能否被确认？
2. 当前状态是否可用于这次用途？
3. 下一步动作还缺什么必要前提？

“当前内容符合预期”不证明原动作造成了它，但可能足够用于阅读、比较或新分析。
账本确认尚未完成也不自动意味着原生执行仍在进行。锁和阻断必须保护明确的资源，
不能将原操作的记录问题扩大为整个 Owner 或项目无法观察。

| 下一步 | 所需判断 | 缺口或变化后的继续方式 |
| --- | --- | --- |
| 阅读、探索或比较 | 当前材料可读、范围和限制清楚 | 来源未知仍可读；显示限定，按需新观察 |
| 覆盖文件 | 明确用户请求、目标、必要的内容与并发条件 | 仅拒绝冲突覆盖；保留草稿，比较、合并或另存 |
| 在同一原生会话运行 | 会话身份、实际执行内容和 Owner 的运行条件 | 不绕过未确认的原生执行；独立工作按自己的前提进行 |
| 复核旧结果 | 当时的输入和执行材料是否存在 | 缺失就限定复核范围；不拿当前文件冒充历史输入 |
| 提出或发布一项科研主张 | 与这句话有关的检查、依据、假设和反例 | 补有关证据或收窄主张；不要求全项目来源完美 |

上表说明上层的用途判断与具体动作条件，不生成 Core 的 browsing、analysis、publication
许可矩阵。Core 传递已知材料、观察范围和限制；由具体科研用途判断缺口的影响。
字段缺失不自动使对象无效，原生条件不满足则只限制相应动作。

未知执行不能因用户接受不确定性就当成从未执行。
安全替代路径应减少对缺失信息的依赖，并说明其适用范围。

## 实施顺序与完成条件

每次只选择一个具体用户动作及其真实 Owner。下面的顺序保留讨论中的渐进路线，
后续项不是当前项的前置条件；实际缺口改变时可以修正顺序，不为了完成表格建设框架。

| 顺序 | 用户动作与选题 | Owner 与完成条件 |
| --- | --- | --- |
| 当前基线 | 原生补丁返回、结算尚未确认时读取当前文件；外部随后改盘后再读 | Files 已分离原生访问与写入结算保护；Owner 验证与包构建已完成，应用组合仍未选定。证据与限制见 Status |
| 下一项 | 无窗口、无注释服务时读取、搜索和修改项目文件 | Files 分离基础能力与可选交互依赖；公开调用完成真实文件结果，缺少可选能力仅影响对应入口，不新增权限配置任务 |
| 随后 | 外部文件变化后保留编辑工作并继续 | Editor 与 Files 保留旧基线、当前磁盘和草稿；比较、合并或另存；过期覆盖被拒绝，无关阅读继续 |
| 按用例选择 | 原操作结束或结果未知后增加观察与复核材料 | 实际 Owner 或上层保留原请求，用显式引用关联后续材料；当前状态与原动作归因分开，不重放、不覆盖历史 |
| 按用例选择 | 从一项明确声明的关联找回有关动作与回报 | 先用现有记录入口证明缺口；确需 Core 查询时限定记录范围和分页，不建立图编排或推断因果 |
| 按用例选择 | 解释一项具体科研主张的依据与缺口 | 领域或论证层先展示材料、检查、假设与反例；只有需要时才生成局部关系视图和指标 |
| 独立集成 | 工作台与外部 Agent 使用上述能力完成选定研究流程 | 明确选择组件和 SDK，证明真实接线；Owner 单仓结果不能替代产品流程 |
| 后置，待需求明确 | 多用户共享、远程访问或实际权限隔离 | 选定具体场景后再设计最小权限机制；不阻塞前面的本地工作流 |

Core 后续工作的选题约束：

- 优先保持公开观察通道独立于窗口、编辑缓冲区、全项目证据完整性和原操作结算。
- 在 Owner 用例确实暴露公共缺口时，才修 Core 的对象定位、路由、资源或观察封套。
- 近期不新增权限体系、角色模型、授权配置或审批；已有机制妨碍选定本地流程时，单独选择最小简化。
- 对已受理动作保留原请求、明确标识的重复送达保护和已知回报，避免丢失回报后自动重执行。
- 逐项审查提交、取消和生命周期机制保护的具体损失与成本，不为维护抽象保证保留整套通用框架。
- 审查重复校验、持久化和状态模型时，说明每处信任边界与用户后果；不以统一机制为目标。
- 不预先实现完整 Context Envelope、因果模型、全局证据图、可信度等级、统一版本管理、通用风险或恢复引擎，以及新的 Agent 产品。

讨论中的证据阶梯与多维指标留在主张层按需试验，不作为近期 Core 工程。
覆盖率需要明确已声明的分母；稳健性比例只描述已测试设置；未检查不等于失败；
无校准依据不能将评分表达为真值概率。缺口说明必须回答不知道什么、影响哪个用途、
怎样补证，以及是否可以换一条路继续。

## 验收、接续与计划维护

一条代表性验收路径是：打开已有项目，读取外部数据，修改脚本，接纳一次外部改盘，
运行选定代码，读取对象或产物，并在一次回执丢失后继续与它无关的工作。
按所选 Owner 分段验收，不将整条集成流程变成 Core 单仓任务的门槛。

检查应证明具体结果：实际读到了什么，哪些字节改变，草稿是否保留，执行了几次，
被拒绝的覆盖是否保持原字节，原请求是否仍可定位。测试普通继续路径，也测试真正
应该阻止的动作。读取成功不替代写入检查，夹具不替代真实 Files 或 R 结果。

记录增长、内存、等待和延迟只有在相关瓶颈出现时才测量并比较；观察次数不应机械
等于科研记录数。不承诺尚未测量的性能收益，不为收尾扩大验收范围。

每次继续工作：先读本文件、当前 Architecture 和所选 Owner 的要求，核对 Status 与
Git 状态；再写下用户动作、完成条件、必要规则与失败后的继续路径。规则无法说明
保护的具体损失时，应考虑删除、降为提示或换用成熟工具。
使用 Skills、Loop、Graph 作为设计视角，选择与当前用户动作相关的验证与实现边界；
不把三者变成每次交付的统一门槛。

一次交付只证明其选定边界。组件提交、SDK 刷新、应用锁、组合验收和正式发行分别处理；
Core 的旧职责退出不自动完成消费端迁移。本轮破坏性升级仍使用新项目与存储，
本计划不恢复旧数据迁移或兼容要求，不自动重启用户 Host 或 R 会话。

原则、取舍或实施顺序改变时修改本文件；当前事实与验证结论改变时更新 Status。
Git 保存修订历史。新会话不应凭记忆重建计划，也不把这里的候选机制误当成已经实施的契约。
