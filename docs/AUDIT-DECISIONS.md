# 对审核报告与架构评审的取舍

设计基线：2026-10-10。输入包括用户提供的 [原始审核报告](review/USER-REPORT.md)
与后续关于入口、工具组合及核心扩张的评审。原报告缺少可逐项追溯的引用和源码证据，
作为输入保留；当前目标以 [Architecture](ARCHITECTURE.md) 与
[Mission and plan](MISSION-AND-PLAN.md) 为准。以下决定不证明新代码已实现。

## 本轮评审：成立的判断与需要收紧的推论

关于核心臃肿的判断成立。上一版虽将规划留给外部 Agent，却仍以“接入工具—统一
分派—领域适配”的链条组织核心，并把公开协议入口列为首个交付。它没有明文要求
每项科研方法一个入口，但缺少直接使用外部能力的路径，足以诱导后续建设集成平台。

| 上一版存在的问题 | 本轮纠正 | 以后怎样判断 |
| --- | --- | --- |
| Core 的职责包含 transport adapters，CLI/MCP/HTTP 被并列为入口建设 | Core 提供独立程序边界，可选接入层单向依赖它；界面、协议与传输不混为核心模块 | 新客户端的兼容问题是否被限制在接入层 |
| 图示只有经 Core 分派的工具链路 | 图示加入 Agent 直接使用原 CLI/SDK/MCP 的路径 | 已有能力能否在不注册到 Rho 的情况下使用 |
| 工具描述与目录暗含汇总全部能力 | 只说明 Core 自己承担的能力；原生工具保留原文档与接口 | 新工具是否被迫重复包装、重写类型或进入统一目录 |
| 领域适配器被列为核心组件 | 原生执行方与领域 Owner 在 Core 逻辑边界之外，仅为选定受管动作衔接 | 原生语言与外部服务的差异是否渗入核心语义 |
| 第一阶段重新建立文件读取入口 | 从有附加价值的受管执行与等待者分离开始，普通读取复用现成工具 | 相比直接调用原工具，Core 到底补足什么保证 |
| 固定终点要求统一接入协议、外部入口与独立 SDK | 按真实消费者选定，不为完成路线图而建设框架 | 必要程序边界够用时能否完成交付 |
| 共享机制必须凑足两个流程 | 由可证明的缺口决定，不用流程数量代替工程判断 | 能否解释新增机制保护的具体行为 |
| 执行保护没有充分限定到受管路径 | 只对声明范围的动作、寿命与保留期限负责；外部变化不补造受理和因果 | 是否声称追踪或保护了实际未受理的动作 |

评审不能进一步推出“Core 不需要稳定接口”或“所有动作都交给万能执行工具”。
Agent 能组合代码，仍需知道接口、权限、真实对象与结果限制。专用工具可能有价值，
但应由真实任务证明。拆分接入层也不意味着另建服务、仓库或插件框架。

评审中提到的“理解意图”不是上一版架构文件中的原句；它是对设计风险的提醒。
新职责明确由调用方选择行动，Core 只处理已选择的动作，不把这项风险写成已发生的
实现缺陷。同样，文档仍需保留原生条件、重试与结果未知的事实，不将可靠性归为
应当删除的“传统编程思维”。

## 已核对的相关实践

- [MCP 架构说明](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)区分协议与传输，明确不规定应用怎样使用模型或管理上下文。支持接入与核心行为分离；不要求 Rho 代理全部 MCP 服务，也未替 Rho 提供原生执行保证。
- [Anthropic：Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)展示按需读取接口、用代码组合调用和在执行环境处理数据的方式。支持减少预加载和中间结果搬运；其代码执行成本与隔离要求仍需实际环境承担。
- [Cloudflare：Code Mode](https://blog.cloudflare.com/code-mode-mcp/)用 `search()` 与 `execute()` 访问已有 API 描述与调用能力。这个案例说明底层能力数量不必决定模型可见入口数量；不能据此要求 Rho 自建这两个工具、聚合所有 API 或复制其性能结论。
- [OpenAI：Sandbox Agents](https://developers.openai.com/api/docs/guides/agents/sandboxes)区分 Agent harness 与执行计算环境。支持将模型循环、工具选择与真实执行边界分别归属；不意味着 Rho 必须采用该 SDK、部署容器或建立另一个 harness。
- [Anthropic：Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)指出直接包装软件功能或 API 端点可能不适合 Agent，工具选择和粒度应通过实际评估改善。支持按任务选择专用工具或代码组合，不把其中一种形式提升为通用定律。

上述是外部实践；将它们用于 Rho 的职责收缩属于本项目推论。它们不证明 Rho 的
实现、适用性或性能。核对没有选定协议、SDK、框架或隔离产品的实现版本。

此前核对的 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
与 [ReAct 原论文](https://arxiv.org/abs/2210.03629)支持从简单方案、真实环境反馈和任务
评估出发；并不能替科学运行时选定存储、并发或接续语义。

## 原报告建议的后续取舍

| 报告建议 | 本项目决定 | 必须保留的事实 |
| --- | --- | --- |
| 减少模块、网关与中间件 | 采用；已有工具优先，受管缺口才进入 Core | 简化应减少实际调用与维护成本，不能把同一兼容框架搬到插件 |
| QuerySnapshot 合入模型上下文 | 不建快照模块，按需读取实际 Owner | 上下文无法证明当前世界未改变；保留旧字节需要真实用途 |
| 工具框架替代 OperationGateway | 不预选框架，只补必要受理与回报 | 框架名称不能保证去重、原生效果或并发写入 |
| 向量检索、账本与派生记忆 | 留在调用方的实际检索需求中 | 受管执行记录不成为模型记忆或环境总账 |
| 模型循环替代 Planner，多 Agent 按需加入 | 由外部 Agent 运行时决定 | Core 不增加推理、协作或图调度运行时 |
| Serverless、分布式事件流、弹性云 | 仅在选定部署有实测需要时考虑 | 本地流程不为未来规模预建云设施 |
| 零信任、OpenShell、静态扫描 | 仅作为具体执行边界的候选 | 产品名称与路径检查不能证明隔离，模型也不能扩张权限 |
| 日志支持审计与回滚 | 记录帮助定位；撤销取决于实际 Owner | 取消、恢复字节和重新执行不是同一行为；外部动作不自动受管 |
| 展示推理过程 | 需要时提供已选动作、可检查的理由与结果 | Core 不取得或保存模型隐藏思维链 |

原报告的 MemAgent 能力、RLHF/RLAIF 比较、风险数量、SkillSpector 效果及内嵌工具
消除外部延迟等说法未有本次核实证据，不进入约束。统一“允许 5% 下降”或“拦截率
超过 90%”也不是验收门槛；正确性条件和性能目标必须落到明确任务与测量方法。

## 给新增机制安排最小验证

| 要验证的问题 | 最小实验 | 通过标准 |
| --- | --- | --- |
| 新方法是否要求 Core 扩张 | 同一执行能力运行两个不同任务脚本 | 不增加方法入口，结果可检查；不能只用相同脚本改参数冒充组合能力 |
| 直接工具是否需要包装 | 先用原 CLI/SDK/MCP 完成选定任务 | 已能满足的部分直接保留；仅记录真实受管缺口 |
| 受管路径是否增加价值 | 结束一个等待者，再读取同一原生任务 | 原执行可定位；等待结束不停止或重新派发 |
| 去重与接续是否可信 | 重复送达、受理失败、派发后中断、回报保存失败 | 原请求可定位或明确未知；不重跑、不伪造成功 |
| 直接外部变化是否被错误归因 | 外部工具改临时文件或改变原生对象 | 能观察新状态，但不补造 Core 受理历史；Owner 检查当前条件 |
| 接入是否侵入核心 | 在真实消费者需要时增加一种接入 | 复用既有程序边界与约束，不改变核心以兼容客户端 |
| 工具与代码组合哪个更适合 | 比较同一实际任务的两种可用方式 | 根据任务完成、上下文成本与维护负担选择，保留失败证据 |

这些验证进入所选功能的完成条件，不再建立一套先于工作流的通用评估平台。
