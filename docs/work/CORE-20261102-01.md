# CORE-20261102-01：Windows 上逐次写入的输出一起提交

## 来源与范围

用户在 Rho 开始三平台 CI 与 npm 发布，并让 Rho 按需调整其余问题。Rho 的 CI 在 GitHub 的
windows-2022 运行器上用本仓 `6f83226` 的 MSVC dev 构建运行 Rho 的测试。“修复是新的身份”一项在
macOS 上约 2 s，在 Windows 上 47–48 s，第 6 次运行超过它的 60 s 上限。本次只改 Windows 的输出
泵；Unix 路径、存储格式、限制值与受管语义不变。

## 现象

Rho 的诊断运行（[41377127229](https://github.com/YuLab-SMU/Rho/actions/runs/41377127229)，
`6f83226`，R 4.5.1 与 4.6.2）经 Rho 服务逐项计时：

| 运行 | macOS arm64 | windows-2022 |
| --- | --- | --- |
| R 向 stderr 写 200 行 `message()` | 0.2 s | 3.1–3.4 s |
| R 向 stderr 写 2000 行 | 0.2 s | 20.2 s、34.8 s |

R 4.6.2 那次运行期间一次 `lookup` 等了 20 s 才返回，Rho 据此把仍在运行的结果记为未知。Rho 的
修复测试正写 2000 行，单独运行 36–40 s。

## 原因

Windows 的读取线程以阻塞读取管道，进程的每次写入都作为一次读取到达，经通道交给持有循环。
`read_once` 对每个事件单独调用 `record_output`：写一个 blob 并同步，再刷新运行记录。2000 次
逐行写入就是 2000 次这样的提交；macOS 上同样的写入在一次就绪读取中最多取 64 KiB，只有几次提交。
逐次提交还消耗块数上限（默认 4096）：逐行写入超过上限后，字节只计数不保留。

## 改动

`read_once` 把自上次排空以来排队的字节合在一起提交，每次最多一个 blob 块（`BLOB_CHUNK`，64 KiB，
读取时超过它的输出 blob 视为损坏）；遇到结束或读取失败，先提交已排队的字节，再记录结束或错误。
读取线程、通道与记录字段不变。

回归 `many_short_writes_are_retained_together_within_the_chunk_limit`：`perl` 以自动刷新逐行写
5000 行，块数上限设为 512，要求全部字节保留、无保留错误、块数不超过上限。

## 同时看到、不属于 Core 的问题

同一诊断里，项目路径含 `%OS%` 时 R 以 `0xC0000005`（Core 报告为 `Code(-1073741819)`）结束。
由 Node 直接启动 R 4.5.1 与 4.6.2、绝对路径脚本含 `%OS%` 时同样崩溃，相对路径不崩溃，所以是 R
自身的问题。Core 如实报告了退出码；Rho 的契约原先要求退出码不小于 0，已在 Rho 改为 i32 全范围。
