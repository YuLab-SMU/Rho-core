## 实际交付与验证

交付（源码、契约与回归同一提交）：

- `src/store.rs`：`state_dir` 独占锁（`store.lock`）与项目绑定（`store.json`）；每个身份
  一个记录目录（身份哈希），`pending/` 暂存后整目录 rename 受理；事实文件临时写入、
  fsync、rename、目录 fsync；`forget` 先移入 `trash/` 再删除。
- `src/run.rs`：受理后、启动前持久写入 `dispatch.json`；`spawned.json`、`cancel.json`、
  `outcome.json` 写入失败不改变原生事实，经 `RunView::unsaved` 报告并在之后读取时重试；
  重开后按已保存事实推出 `NotStarted` 或 `Detached`，不推测；运行锁作为标准输入由进程组
  继承，用于观察重开后是否仍有进程（`present`）。
- `src/lib.rs`：载入已有记录；读不出的记录阻止其身份（`RecordUnreadable`）；`max_records`
  计入全部存储记录；`forget`、`unreadable_records`；未持有的运行不发信号、不记录取消。
- `src/fault.rs`：`fault-injection` 特性下由 `RHO_CORE_CRASH_AT` 在指定点 SIGKILL 自身，只经
  本仓库 dev-dependency 启用。
- 依赖：`serde` 1.0.229、`serde_json` 1.0.151（`Cargo.lock` 固定）。

故障窗口与实验（除第一行为 `tests/managed_run.rs` 的进程内存储失败外，其余在
`tests/restart.rs` 中，宿主进程被 SIGKILL 后由新实例重开）：

| 故障窗口 | 中断位置 | 重开后观察 | 派发次数 |
| --- | --- | --- | --- |
| 受理保存失败 | `records/` 设为只读（进程内） | `Storage`，`lookup` 为 `NotFound`；恢复后受理一次 | 0 → 1 |
| 受理未提交 | `staged` | `NotFound`，再次提交受理一次 | 0 → 1 |
| 受理已保存、未派发 | `committed` | `NotStarted`，结论保存，第三个实例读到相同事实 | 0 |
| 派发已记录、未启动 | `dispatched` | `Detached { pid: None, present: false }` | 0 |
| 已启动、未记录 | `spawned` | `Detached { pid: None, present: true }`，放行后 `present: false` | 1 |
| 持有中宿主被杀 | 测试 SIGKILL | `Detached { pid: Some, present: true }`，进程存活，关闭不发信号 | 1 |
| 原生已完成、回报未保存 | `exited` | `Detached { pid: Some, present: false }`，保留输出可读，不声称退出状态 | 1 |
| 取消已保存、确认丢失 | `cancel-saved` | 取消请求保留，`term_sent_at` 为空，状态不报告停止 | 1 |
| 记录损坏 | 改写 `request.json` | 出现在 `unreadable_records()`，提交为 `RecordUnreadable` | 0 |
| 容量与删除 | `max_records = 1` | 之前实例的记录计入容量；非终态 `forget` 被拒；删除后同身份再执行 | 1 → 2 |

受理已保存的 5 个崩溃窗口与正常结束后重开，均在重开后用 4 个并发提交检查重复送达只
得到 `Existing`、派发次数不变；其余实验检查各自表中的派发次数。另有同一 `state_dir`
第二个实例与换项目打开被拒的检查。

实施中复现并修正的失败：

1. 多线程进程中 `kill(getpid(), SIGKILL)` 返回后线程仍继续，`staged` 实验在并行运行时
   完成了 rename；崩溃点改为发信号后 `pause()` 阻塞。
2. 测试在宿主保存 `spawned.json` 之前杀死宿主，得到 `pid: None`；宿主改为 `submit` 返回后
   写就绪标记，测试等待它再杀。这是测试的时序错误，`pid: None` 本身是正确报告。
3. drop 后立即重开偶发“state dir 正被另一个 Core 使用”。改为 drop 等持有线程放开存储锁，
   并去掉 `pre_exec`（运行锁改作标准输入）；仍有偶发后，`open` 对锁冲突有界重试 500 ms。
   推测原因是其他线程 fork 出的子进程在 exec 前短暂持有锁描述的副本，未能直接证实。
