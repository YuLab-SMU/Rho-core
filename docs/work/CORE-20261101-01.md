# CORE-20261101-01：Windows 移植后的 Unix 构建与宿主修复，macOS 与 Linux 复验

## 用户决定与范围

用户要求 Rho 先支持本机（macOS arm64）与 Linux，Windows 随后由用户在另一个克隆完成。
Rho 要在一个包里放同一 Core 提交的各平台二进制，因此选用含 Windows 移植的 `7e424b3`。
在 Linux 上构建时发现它在 Unix 上不能编译。本仓只修 Unix 侧，Windows 实现没有改动。

## 发现

[`1e95dd7`](https://github.com/YuLab-SMU/Rho-core/commit/1e95dd7) 的说明写的是 Unix 路径
“构造上不变”。实际上它没有在 Unix 上编译过，本机的 debug 二进制仍是 `4f5bed8` 构建的
0.5.1 产物（摘要 `434a92fc…`）。

- **编译**：库有 8 处错误（`READ_BUFFER`、`SystemTime`、`StreamInfo` 未引入，`custom_flags`
  缺少 `OpenOptionsExt`，以及未使用的导入和变量）。二进制缺少 Unix 的 `pipe_name`、
  `is_socket` 所需的 `FileTypeExt` 和信号模块的 `Read`。测试的 `Host` 初始化在 Unix 上
  缺少 `stop_file`。
- **宿主一启动就退出**：信号管道的读端同时交给了 `OwnedFd` 和用 `from_raw_fd(fds[0])`
  新建的 `File`。函数返回时前者关闭了描述符，宿主第一次读就得到 EOF，以
  `"signal_error":"unexpected end of file"` 停止。macOS 上 `tests/host.rs` 因此 9/9 失败。
  `4f5bed8` 把 `read` 移入 `File`，没有这个问题。
- **Linux 无法编译对端检查**：移植把按系统分开的 `peer_uid` 合成了只有 macOS 才有的
  `libc::getpeereid`。`4f5bed8` 在 Linux 上用 `SO_PEERCRED`。
- **关闭时不再删除自己的 socket**：`4f5bed8` 在关闭 Core 前删除本宿主绑定的 socket 文件，
  并比较 dev/ino，不会删掉后来宿主的文件。移植后只有监听器的 `Drop` 无条件删除。

## 改动

按 `4f5bed8` 的行为恢复：`READ_BUFFER` 回到 Unix 实现；信号读端由 `Signals` 唯一持有；
macOS、Linux 和其他 Unix 各自的 `peer_uid`；关闭时由宿主按 dev/ino 删除自己的 socket，
去掉监听器的 `Drop` 和三个没有调用者的辅助函数；补上缺少的导入和测试字段。

## 证据与检查

| 平台 | 构建 | 结果 |
| --- | --- | --- |
| macOS 26.7.2 arm64 | 默认目标 | 格式、Clippy、81 项回归、`managed_run` 示例通过 |
| Debian 12 arm64（OrbStack，原生） | `aarch64-unknown-linux-musl` | 同上，全部通过；静态链接 |
| Ubuntu 25.04 amd64（OrbStack，Rosetta 转译） | `x86_64-unknown-linux-musl` | 第一次：`managed_run` 卡住 25 分钟后终止（16 项完成 7 项）；第二次全部通过 |
| Windows | 本机 `x86_64-pc-windows-gnu` | 仅 Clippy 类型检查通过；MSVC 构建与回归没有重跑 |

卡住时测试进程的多数线程停在 `rt_mutex_schedule`，夹具子进程在等 FIFO 另一端。
Rosetta 下 gdb 取不到寄存器，没有拿到调用栈。为判断来源，单独反复运行
`managed_run` 测试二进制，8 路并发、每路 25 次：

| 构建 | 运行环境 | 卡住（60 秒超时） |
| --- | --- | --- |
| 本次，musl | x86_64，Rosetta | 5/200 |
| 本次，glibc | x86_64，Rosetta | 3/200 |
| `4f5bed8`，glibc | x86_64，Rosetta | 5/200 |
| 本次，musl | Linux arm64，原生 | 0/200 |
| 本次 | macOS arm64，原生 | 0/200；另有 1 次在负载下“timed out waiting for task start” |

串行反复运行时，Rosetta 下 musl 50/50 通过，原生 arm64 50/50 通过。卡住在移植前就存在，
与 libc 无关，只在 Rosetta 转译的 x86_64 上出现过。

## 未验证与开放问题

- Rosetta 下整进程卡住的原因未定。真实 x86_64 硬件没有试过，所以不能断定这只是转译环境的问题。
- Windows 只做了类型检查。Linux 平台脚本（跨 UID、命名空间、内核重启）这次没有重跑。

证据保存在相邻 Rho 的 `work/platforms-0.5.2/`。没有发布、安装或替换用户的 Host。
