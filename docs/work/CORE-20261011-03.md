## 实际交付与验证

- 实施开始时 Core 工作区干净，main 跟踪 origin/main；本轮只在 Core 记录源码变更。
- 规划阶段已实测：Ubuntu 25.04/x86_64 在 OrbStack 上运行；正常 boot_id 是 tmpfs 覆盖文件，临时重新挂载 proc 后同 PID namespace 的 boot_id 不同且来源为 procfs。旧代码仅比较字符串，可能宣布仍活着的任务 Gone。
- 已先用旧二进制在 Linux 复现：原任务仍活着，仅切换 proc 视图就被报告 `Gone/BootChanged` 且释放；派发计数为 1。修复后的三个身份边界实验不再错误解除保护。
- 最小修复：[ProcessContext](../../src/record.rs) 增加必填 `boot_id_scope`，公开 `BootIdScope::{Kernel, LocalView}`。Linux 从同一已打开文件句柄读取标识并检查文件系统来源；procfs 为 Kernel，其他来源为 LocalView。macOS 的启动会话 UUID 为 Kernel。读取失败保留未知。
- 只有两个 Kernel 标识不同才能证明 BootChanged；否则仅当标识、来源范围、PID 命名空间均相同时，进程表才可证明消失。其他视图变化仍保护记录，不发信号、不推断退出码、不重派。沿用可信本地 OS 视图前提，不新增隔离保证。
- 存储格式升为 3，不迁移旧格式；旧格式 2 被拒且原数据保留。CLI 命令与退出码不变，完整操作记录增加来源范围。同步了[受管运行](../MANAGED-RUN.md)、[信息模型](../INFORMATION-MODEL.md)与[宿主契约](../HOST-CLI.md)。
- 新增独立 [Linux 验证脚本](../../tests/linux_platform.py)，四个入口 `uid`、`namespace`、`prepare-reboot`、`verify-reboot`，显式接收二进制和一次性夹具根目录；脚本不自行重启 OrbStack。

## 失败证据与适用限制

- macOS 初次受沙箱影响读取不到过程上下文，前置夹具失败；该次没有计为误判复现。随后可读取身份的实际检查复现旧行为并在修复后通过。初次 Clippy 的测试模块位置错误、Linux 的 libc 文件系统类型转换编译失败均保留；最终分别修复并通过。
- Linux 原不可执行文件启动失败夹具返回 Finished/Code(127)，没有给出同步 spawn 错误；在本地持久文件系统仍可重复。独立探针确认 posix_spawn 与直接 exec 错误传播不同。没有把退出码 127 推断为 NotStarted，也没有改生产执行语义；回归改用固定执行器参数含 NUL 的确定同步启动失败，验证已受理但未派发且不重试。两平台最终通过，原失败日志和源码快照保留。
- 补充契约检查的临时检查器先遗漏必需执行器配置，之后 Mac 路径超过 Unix socket 上限，最后字节比较未考虑 CLI 固有末尾换行；各次失败均保留，修正检查器后通过，没有据此改 Core 或扩大验收范围。
- 未运行 Agent 经 CLI 的模型评估；未添加 CI、跨仓集成或 SDK 刷新；未验证断电或 OS 崩溃的持久性，也未验证 macOS 的跨 UID 拒绝。此次正常 OrbStack 内核重启不能替代这些结论。
