## 发现：夹具记下的是 `cat` 的 pid

每次完整回归后都留下一个仍在运行的 `sh.exe`，轮询已被删除的 `gate.release`。逐个单独运行
`restart` 的 23 个测试，只有 `a_changed_local_boot_view_does_not_prove_a_live_run_gone` 留下进程。

Windows 夹具用 `echo $(cat /proc/self/winpid) >> dispatches.log` 记录自己的 pid。命令替换里的
`/proc/self` 是读取它的 `cat`。实测由 Node 启动的 `sh -c` 中，`/proc/self/winpid` 得到一个已退出的
pid，`/proc/$$/winpid` 得到的正是被启动的 sh 进程。这条测试在打开闸门后等待记录的 pid 消失，等的是
早已退出的 `cat`，于是立刻结束并删掉临时目录，脚本再也读不到 `gate.release`。

`managed_run.rs` 因同一误读认为 “MSYS sh 会 re-exec，记录的 pid 与派发的 pid 不同”，Windows 上
跳过了两处 pid 比对；`WINDOWS.md` 写了同样的说法。

## 改动

- `restart.rs` 与 `managed_run.rs` 的 Windows 夹具改用 `/proc/$$/winpid`。
- 去掉 `logged_pids_match_core_pids()`：两处 “记录的 pid 等于 Core 报告的 pid” 在 Windows 上也
  断言，并通过。
- 更正 `WINDOWS.md` 的 re-exec 说法。

## 发现：控制台事件不能让宿主按顺序停止

Rho 在 Windows 上要停止自己启动的宿主。2026-11-02 00:28 起用本次构建的二进制实测（Rho 的
`work/windows-0.5.2/probe2/`）：宿主由 Node 以无窗口的控制台启动，辅助进程附着到该控制台
发出事件。

- Ctrl-Break：宿主约 0.6 s 内以 `0xC000013A`（`STATUS_CONTROL_C_EXIT`）退出，没有 `shutdown`
  行。`report_ctrl` 返回 0，系统接着调用默认处理，默认处理结束进程，关闭路径来不及运行。
- Ctrl-C：宿主没有反应，12 s 后仍在运行。插件的 Python 会话以同样方式启动时也收不到 Ctrl-C，
  原因是继承了关闭的 Ctrl-C 处理；宿主是否同因未单独验证。
- `RHO_CORE_STOP_FILE`：文件出现后约 0.1–0.2 s，宿主打印 `"signal":15` 的停止报告并以 0 退出。

因此 `WINDOWS.md` 里“ctrl 事件对应 SIGTERM/SIGINT 的优雅停止”在 `c3dbeca` 上不成立，已按实测
更正。Rho 改为在 Windows 上给自己启动的宿主设置 `RHO_CORE_STOP_FILE`，关闭时创建该文件；二进制
未改，四个平台仍可用同一提交的 Core。

## 未验证与开放问题

- 每次完整回归在 `%TEMP%` 留下约 15 个只剩空子目录的 `.tmp*`（2026-10-28 移植时的运行也有）。
  删除时刚结束的进程尚未关闭句柄，文件处于待删除状态，目录删不掉。不影响 Core 行为，未处理。
- Windows 的客户端只接受管道名作 `--socket`，`<state_dir>/host.sock` 不会映射到管道。不是本宿主
  启动的调用方（如重启后的 Rho）要从 `\\.\pipe\` 中按 `rho-core.<hash>.host.sock` 查找。Rho 现在
  这样做；是否在客户端映射由 Core 决定，会改变二进制。
- `RHO_CORE_STOP_FILE` 的文档说明仍是测试用，Rho 现在依赖它停止 Windows 上自己启动的宿主。
  是否把它定为正式接口，以及 ctrl 处理是否改为返回 1 让 Ctrl-Break 走关闭路径，由 Core 决定；
  后者会改变二进制，需要重建四个平台的 Core。
- Linux 平台脚本与 Rosetta 卡住的开放问题不变。

证据保存在相邻 Rho 的 `work/windows-0.5.2/`（`core/`、`core-lf/`、`core-fixture/`）。没有发布、
安装或替换用户的 Host。
