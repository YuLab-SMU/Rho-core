# CORE-20261107-01：编进二进制的两份契约文档按 LF 检出

## 来源与范围

Rho 的 [#112](https://github.com/YuLab-SMU/Rho/issues/112) 第 7b 项：在 Windows 上从源码构建 Core 时，
`src/activity.rs` 与 `src/lib.rs` 用 `include_str!` 编入 `docs/ACTIVITY.md` 与 `docs/MANAGED-RUN.md`，
而 `.gitattributes` 只固定了 `vendor/jet-core/**` 与 `patches/jet/**` 的换行。报告者用 LF 克隆避开了
它，没有实际构建 CRLF 版本。用户要求核实并解决。本次只改检出属性；源码、契约文本与构建设置不变。

## 现象

Windows 11 x64（10.0.26200），Git for Windows 的系统配置为 `core.autocrlf=true`，Rust 1.97.0 与 MSVC。
用 Rho CI 的构建参数（`CARGO_PROFILE_DEV_DEBUG=0`，`cargo build --locked --target x86_64-pc-windows-msvc`）。
在二进制中查 `docs/ACTIVITY.md` 的前三个长行，看每行之后是 CRLF 还是 LF。

| 二进制 | 两份文档的检出 | 三行之后 | 大小 | SHA-256 前缀 |
| --- | --- | --- | --- | --- |
| `8bed8ef` 的新克隆 | `w/crlf`，CR 共 72 + 272 = 344 个 | CRLF | 4,616,192 B | `d4449c62ccd7` |
| Rho 0.5.5 包内 CI 构建的 `win32-x64` Core（`8bed8ef`） | CI 先设 `core.autocrlf false` | LF | 4,616,192 B | `16daf3f2125c` |
| `8ef933a` 的新克隆 | `w/lf`，`attr/text eol=lf` | LF | 4,615,680 B | `533adf89aff2` |

所以 CRLF 检出确实改变了编进二进制的契约文本。三个二进制都有 78 处 `C:\Users\<用户>\.cargo\registry\…`
路径：本机构建的是本机用户名，CI 的是 `runneradmin`。这是 #112 第 7d 项，与换行无关，这里没有改。

## 原因

`include_str!` 按字节编入文件；Git for Windows 默认在检出时把文本文件的 LF 换成 CRLF。Rho 的 CI
在检出前设了 `core.autocrlf false`，所以 CI 的 Core 不受影响，在 Windows 上按默认设置克隆的人会受影响。

## 改动

`8ef933a` 在 `.gitattributes` 中把这两个文件设为 `text eol=lf`。

没有运行格式、Clippy 与回归：LF 检出的编译输入没有变化，CI 一直用 LF 检出构建。Rho 的
`components.json` 仍选 `8bed8ef`；在它之前的提交上，从源码构建仍需 LF 检出，Rho 的 HEADLESS 写明了。
