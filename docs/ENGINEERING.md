# 开发 Rho Core

Core 靠在真实调用上试用、看结果、再改进来开发。每一步产生一个具体结果：一次真实
调用、一次故障实验、一个 Agent 或消费者真正用上它。下一步从分析这个结果得出。文档
记录结果已经说明的事情：已建成行为的契约、已确认的教训和当前状态。它们不为还没有
真实调用方的能力预写接口、检查表、阶段终点或禁用清单。先于结果写下的规则会把猜测
变成要求，之后的工作就按猜测、而不是按实际需要来评判。

先读 [进度](PROGRESS.md) 了解各部分所处的位置，[架构](ARCHITECTURE.md) 了解当前职责
与应保护的事实。已建成的行为见 [受管运行](MANAGED-RUN.md)、[信息模型](INFORMATION-MODEL.md)、
[宿主与 CLI](HOST-CLI.md) 与 [活动观测](ACTIVITY.md)。

## 什么固定，什么开放

**保护**的是[已有工作与诚实事实](ARCHITECTURE.md#固定的边界)：原请求和已经给出的
去重承诺、不确定不授权重跑、各项事实及其依据、观察与受管的区别、已有权限和部分结果。
依赖方向、身份由谁生成和工具接入方式都是可以复核的实现选择，不能用测试或文档将其
固化为智能体必须遵循的工作方式。Agent 正常使用原生工具，Core 只按具体需要选用。

其余能由结果教会我们的都**开放**：下一项能力、API 与命令形状、存储布局与格式、限额
默认值、内部模块与共享机制、性能取舍、测试组织、验证平台、要不要 SDK、协议入口、
迁移或 CI，以及文档怎样组织。这些在真实调用上试过再定。当前值在代码与契约里，评审
过的结果需要时就改；有测试的行为连同测试一起、有意地改。

## 阶段

一项能力按下表推进。不同能力可以同时处在不同阶段，[进度](PROGRESS.md#各部分的位置)
记录各自的位置。

| 阶段 | 问题 | 要产生的结果 | 还不做 |
| --- | --- | --- | --- |
| 1 · 能跑 | 真实调用方能在真实资源上端到端完成吗？已有工具缺什么？ | 先用已有工具做同一件事，再做一次真实运行：命令、输出、记录，以及哪些是模拟或跳过的。 | 通用化、细化契约、补齐所有故障。 |
| 2 · 保证成立 | 要宣称的保证在它覆盖的故障下还成立吗？ | 针对这项主张的故障实验，例如并发重复、等待者离开、提交前后崩溃、存储失败、超限。 | 宣称没有实验支撑的保证。 |
| 3 · 被使用 | 真实消费者（Agent、插件或 Rho）不靠作者帮助能用上吗？ | 真实消费者的运行记录：它做了什么、误解了什么、在哪里失败、怎样恢复。 | 把作者自己会用当作证据。 |
| 4 · 复用 | 第二个不同的消费者也需要同样的东西吗？ | 第二个消费者的运行；据此决定什么成为共享契约。 | 从一个例子抽出通用框架。 |
| 5 · 加固 | 其他部分变化时它还能工作吗？ | 已确认行为的回归、所需平台上的检查、写成指导的教训。 | 没有新证据就重开已定的行为。 |

阶段 2 和 3 可以调换顺序，但任何保证都要先过阶段 2 才能写成保证。阶段 1 求快：粗糙
的命令、临时脚本和夹具都可以，只要标明。严格的检查与成文规则属于阶段 5；用在
阶段 1 的问题上，只会拖慢学习并把猜测固定下来。阶段问题回答了就前进，而不是等某张
清单填满；结果说明早先的问题答错了，就退回去。

## 一次迭代

每次迭代用一次真实运行回答一个问题。

1. **选问题**：上一次结果暴露的最重要问题，或当前阶段的问题。写一段简短说明。
2. **先用已有工具**：直接用 shell、原生 CLI 或库做同一件事，记下它已经提供什么、缺
   什么。说不清缺口，就不进 Core。
3. **做能回答问题的最小改动**，放在实际 Owner 里。先去掉不需要的步骤，再考虑加结构。
4. **运行真实场景**：一次性的项目与状态目录、真实执行方或真实客户端、场景有 Agent 时
   用真实 Agent，以及与问题相关的故障。保留上一次的设置，两次结果才能比较。
5. **亲自看结果**：原生派发次数、实际输出字节、保存的记录、日志和 Agent 的实际动作。
   测试通过只说明这条路径走得通，不说明调用方能据此做对下一步。
6. **分析、改进、记录**，见下文。

说明是几行工作材料，不是另一份文档：

```text
问题：    这次运行要回答什么
基线：    已有工具做同一件事的结果，Core 要补的缺口
设置：    项目、执行方或客户端、Agent 或夹具、要注入的故障、平台
改动：    改什么，在哪个 Owner
看什么：  回答问题的输出、计数、记录或行为
改方向：  什么结果说明这条路不对
```

## 分析结果

**从调用方的任务出发。** 用调用方自己的话写下它要做成的事，例如“等待中断后找回原
运行，不重跑”，再看结果是否做到：要几次调用、要知道多少实现细节，失败时它能否判断
下一步该做什么。

**先观察，再判断。** 观察要说出状态、看到了什么、为什么对任务重要。“宿主 SIGKILL
后同一身份返回 existing，原生派发计数仍为 1”可以据以行动；“重启看起来没问题”不能。
在有帮助的地方测量：派发次数、延迟、存储大小、调用次数、Agent 的步数。也记下有效的
部分，下次改动要保住它。

**给每条观察分类**，类别决定处理顺序：

- *阻断*：任务无法完成、工作丢失或副作用被重复执行。
- *误导*：结果让调用方形成错误判断，例如未知被报成失败、受理被当成已执行、等待超时
  被当成停止、仍在运行的任务被报成已消失。
- *摩擦*：能完成，但要多余的调用、猜测或对实现的了解。
- *打磨*：命名、输出格式等不改变结果的部分。

**找原因和 Owner。** 许多表面问题来自同一个原因，先查最深的一层：

| 层次 | 典型迹象 | 改在哪里 |
| --- | --- | --- |
| 必要性 | 已有工具已经能做，或调用方其实不需要这项保证 | 不进 Core；写调用说明，或删掉 |
| 契约 | 调用方拿不到继续所需的事实，或保证的范围说不清 | Core 契约与实现，连同测试 |
| 实现 | 契约正确，但在某个窗口、平台或并发下不成立 | Core 实现：先复现再修，留下回归 |
| 原生与环境 | 执行方、OS 或客户端的行为与假设不同 | 实际 Owner；Core 只表达观察到的事实 |
| 调用方 | Agent 或消费者误用了正确的契约 | 调用说明、插件或 Agent 环境 |

在能解释大多数观察的最深一层修。改措辞修不好契约问题，加机制修不好必要性问题。

**区分证据类型。** 路径走通、保证在故障下成立、真实 Agent 能用、科学结果正确，是四种
不同的主张，各有各的证据。说明一次运行支持哪些，哪些仍未验证。

**跨运行看。** 只出现一次的问题做局部修复；在第二个场景或消费者中再次出现，才考虑
共享机制和成文的教训。

Core 的历史里有三个例子：

- **常驻宿主**（[CORE-20261011-02](work/CORE-20261011-02.md)）：先实测两种直接做法：
  每次调用开一个持有 Core 的进程，进程退出时运行随之被停止；`nohup` 后台执行两次就
  派发两次。缺口清楚之后才加常驻宿主，并用退出码把“未送达”和“回复未知”分开。
- **启动标识来源**（[CORE-20261011-03](work/CORE-20261011-03.md)）：在 OrbStack Ubuntu
  上用旧二进制复现，只切换 proc 视图，仍在运行的任务就被报成 `Gone`。这是误导类问题，
  原因在契约层：没有区分标识的来源范围。修复后用同样的实验和一次真实内核重启复跑。
- **测试辅助精简**（[CORE-20261016-02](work/CORE-20261016-02.md)）：共享轮询的原型格式化
  后反而多出约 20 行，按结果撤回。

## 改进

- 先修阻断和误导：它们决定结果还能不能被信任。
- 再处理造成多数摩擦的那个原因，通常在契约层，然后才打磨。
- 方向不清时，在同一个真实任务上试两三种实质不同的做法，例如专用命令与代码组合，
  按结果选，其余删掉。
- 每次迭代尽量只做一项重要改动，效果才能归因。改完重跑整个场景，而不只是改动的那一步。
- 性能与资源先在真实规模上测，再优化。已知但还没造成影响的代价写进进度，并写明什么
  结果会触发处理。
- 存储、协议、框架、共享抽象、迁移或 CI 这类新机制，在某个结果证明需要时加入，并说明
  它补上什么、谁负责、失败时怎样检查。名称统一、结构整齐或想象中的未来消费者不是
  理由；已经证明的缺口也不必等凑满几个流程才修。
- 问题回答了就前进。反复修补不再改变观察，或结果与前提矛盾时，换方向并写下原因。
- 不从一个例子推广：框架、共享契约或规则要等到第二个需要它的消费者。

## 检查

检查跟随阶段和主张：阶段 1 的运行需要它的记录；宣称一项保证需要覆盖它的故障实验；
加固需要回归。只有实际执行的检查才算，每项只证明它记录的范围。

- **Core 自身**：依次运行 [README](../README.md#构建与检查) 中的命令，Cargo 构建和测试
  从不并行。并发重复、等待者离开和崩溃窗口用真实进程、真实存储故障和事件同步来制造，
  不靠固定睡眠，也不按内部函数名断言。失败先复现，再修复并留下最小回归；不删除失败、
  不改判据、不反复重跑到通过。Core 的检查不需要模型凭据、相邻仓库源码或用户运行时。
- **平台**：各平台实际验证过的范围记在进度里。旧平台上的证据不自动覆盖新能力。
- **真实使用**：真实 Agent、真实客户端和领域消费者的运行由各自 Owner 负责，Agent 评估
  在 Rho-plugins。它们和确定性回归是不同的证据。
- **执行环境**：使用一次性项目、状态目录和自己启动的宿主。不为验证而启动或重启用户的
  Host 或 R 会话。保留原请求身份、部分输出和未知结果。
- **文档**：检查本地链接与锚点，渲染改动的一批页面并逐页查看，修复后复查受影响的页面。
  [受管运行](MANAGED-RUN.md)与[活动观测](ACTIVITY.md)经 `include_str!` 编进二进制，改动
  它们也要跑 Cargo 检查。

CI 按用户 2026-10-10 的决定暂不配置，需要时由用户选定。

## 记录

- **任务记录**：每项选定的工作在 `work/` 下有一份记录，ID 形如 `CORE-20261025-02`。写明
  用户要做的事和完成条件、实际做了什么、实际执行的检查及结果（包括失败与重试）、未
  验证的范围和下一步。时间按实际时钟记下开始与结束，用带时区偏移的格式；中途有明显
  的等待或暂停就分段。不知道的时间写“未知”，不用提交时间或推测去补。这样之后能查到
  做了什么、什么时候做的、用了多久。
- **[进度](PROGRESS.md)**：各部分所处的阶段、已验证的范围、开放问题、下一步和任务记录
  索引，保持简短。
- **教训**：一个观察到的问题、它的原因和解决它的改动，先留在任务记录里。在第二个场景
  或消费者中仍然成立，再写进它涉及的文档：方法写在本文，边界写在架构，行为写在契约，
  链接两次证据并写明范围。后来的结果与它矛盾时就修改或删除，并说明原因。
- **契约**描述已建成的行为，随实现一起改。

不要先于结果写：没有真实调用方的接口或端点、没跑过的流程的检查表与完成条件、每项
任务都要填的固定清单、预先排好的阶段终点、具体技术的禁用清单。下一次运行的简短说明
就够了。记录中不写凭据、私有项目材料或模型隐藏的思考过程。

## 交付

检查 diff 与 Git 状态，保留无关改动，在 `main` 上提交连贯的改动。推送要先获授权，核对
实际的 remote、分支与账户，推送后核对远程头。不把修改相邻仓库、发布、安装二进制或
替换用户运行中的宿主当作本仓库工作的附带结果；跨仓集成另行选定，在该集成范围内修改。

## 参考

下面的文章提供判断的角度，不替 Core 选择框架，也不是检查表：

- [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)：
  从最简单的方案开始，只有能证明效果更好时才增加复杂度。
- [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)：
  工具的形状与粒度要在真实任务上评估，再根据结果调整。
- [Google SRE：Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)：
  只为能据以行动的问题建立监测，并保持简单。
