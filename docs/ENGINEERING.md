# Rho Core：工程实践指南

设计基线：2026-10-10。本指南将 [核心原则](ARCHITECTURE.md#八实施必须守住的核心原则)
与 [阶段目标](MISSION-AND-PLAN.md#分阶段实施与完成条件) 转为可执行的开发规则。
阶段 1 首个受管流程已有源码与 [调用契约](MANAGED-RUN.md)，选型、命令和限额记录在
其任务记录与 [README](../README.md#构建与检查) 中，实际验证过的平台见
[进度总览](PROGRESS.md)；按用户决定暂不配置 CI。本指南不选定协议、存储产品或观测
平台；后续流程的版本、命令和限额仍在各自任务中实测并记录。

工程工作通过 [进度总览](PROGRESS.md) 和 [任务记录规则](ENGINEERING-MONITORING.md)
持续记录实际动作、时间、耗时与验证。每项选定任务维护一份记录，开工、必要
检查点和收尾更新；记录不替代完成条件，也不增加 Core 运行时的观测职责。

## 一、开工：先选一个可闭合的真实调用

每项工作在任务说明或变更描述中填写下列清单，完成后直接开始所选范围的实现。
清单是工程说明，不为已授权工作增加审批，也不要求新的任务管理系统。

| 项目 | 必须说明什么 |
| --- | --- |
| 调用方动作 | 谁在什么项目中，对哪个执行方和对象，提交什么实际参数 |
| 直接调用基线 | 使用的原工具、版本、实测结果，以及已经提供的持有、查询和去重能力 |
| Core 增加的保证 | 一个原工具无法满足的具体缺口，及受理动作、进程寿命和保留范围 |
| 可观察完成条件 | 原生派发次数、真实输出或字节、原请求与执行身份、一个实际失败 |
| 最小结构与依赖 | 所需程序边界、原生句柄与记录；每个新增机制为何不可由现成能力替代 |
| 资源与数据 | 保护的资源、默认值、配置、超限行为、保存位置、访问与清理边界 |
| 验证与交付 | 实际可运行的命令、失败复现方式、行为检查和此次不承担的保证 |

若原工具已满足全部需要，保留直接调用路径，完成使用说明或调用代码即可。
Core 新增实现从已证明的受管缺口开始。仅为了统一名称、工具描述、目录或模型
可见入口而增加包装，不满足开工条件。具体 API 或版本问题在选型时核对当前官方
文档；既有文档覆盖问题时复用，不按技术名词逐个查库。

## 二、首个受管流程：一个程序调用方与一个原生任务

首个实施选择可信单用户本地项目。普通程序通过 Core 的程序边界提交一个本地
任务；原生执行夹具运行真实进程并产生可检查输出，不伪造科学结果。先用维护中的
执行工具验证基线，再决定 Core 需要补足的关联和持有行为。

1. 用临时项目、临时输出目录与显式选定的执行方；记录所选对象的稳定身份。
2. 调用方持有项目与稳定调用方范围内的请求身份，传入原始参数；Core 检查身份、
   范围和对象关联，执行方检查实际原生条件。
3. 对去重承诺覆盖的动作，先建立可查回的受理，再派发。并发到达的同身份请求
   必须原子地得到一个受理决定；不能先查不存在再分别提交。
4. 原任务进入可观察的运行阶段后结束等待者 A；等待者 B 查询同一原请求与原生
   执行关联，取回同一输出。测试使用事件或原生状态同步，不用固定睡眠猜时序。
5. 验证同身份同参数不重派发，同身份不同参数拒绝，错误对象或范围不会执行。
6. 通过同一能力运行两段不同任务脚本。例如一段生成整数并计算总和，另一段
   根据显式输入生成分组计数；检查各自真实产物，不增加对应方法入口。
7. 记录任务和子进程由谁持有，等待者退出后的行为及清理方式。清理只针对夹具
   资源，确认实际停止与释放；不能仅因父进程退出就报告资源已释放。

阶段 1 可在 Core 进程内保留受理和关联，契约明确这一寿命及失败语义；不因此
承诺磁盘持久化或跨重启去重。若原工具已持有任务，Core 复用其句柄，不能再造
任务调度器。身份不得只靠可能复用的进程号；依所选执行方确认其有效期与唯一性。
阶段 2 才为所需重启保证选择成熟存储和故障验证。需要 Core 启动或持有进程时，
进程及输出限额属于阶段 1 的真实责任，不以“原生工具”名称免除。

## 三、调用契约：必要核心信息必须可按需取得

信息供有访问范围的调用方理解和继续当前工作。提交回报或后续读取可分别提供；
下面是所需事实清单，不是预定字段名、统一结果封装或一组必建端点。

| 信息 | 需要披露的事实 | 避免的误解 |
| --- | --- | --- |
| 能力说明 | 怎样调用、参数与对象要求、实际效果、错误、保证和示例 | 仅靠工具名猜行为，或以模型描述替代契约 |
| 原请求 | 项目与调用范围、请求身份、实际执行方、动作、对象与实际参数 | 修改参数后仍当作同一次请求 |
| 受理与派发 | 已知受理决定、是否可确认派发、查询失败或未知原因 | 受理等于已经产生原生效果 |
| 原生关联 | 可确认的对象和执行身份、句柄、有效范围与来源 | 进程号或名称相同就认定是原对象 |
| 执行事实 | 原生可确认的运行、结束或失败事实，观察时间及已知原生时间 | Core 当前观察时间等于原生发生时间 |
| 回报与材料 | 已知结果或入口、部分性、缓存、来源、容量与续读限制 | 缺失回报等于执行失败，当前内容等于旧材料 |
| 取消与释放 | 请求是否发出、停止和释放是否分别确认 | 取消请求已送达就等于停止或回滚 |
| 保留与接续 | 生命周期、期限、过期与删除行为，以及现在可安全采取的动作 | 缺失记录、读失败或过期授权重新执行 |

未知必须说明未知的是哪一部分以及可确认的依据；取不到依据时说明该限制。
可用的下一步可以是观察原任务、取回已有材料或请求原生取消，不能将重跑隐含为
恢复。结果入口仍遵守对象、访问和材料身份检查；链接或句柄不扩大读取权限。

提交示例和查询示例必须可运行，并包括一个拒绝或未知结果。示例展示取得材料与
检查真实产物，不仅打印“成功”。契约与示例在所选边界保持一个实际维护源；只有
真实导出需求才增加生成或 SDK 工具。直接工具继续使用其原文档，无需全部注册。

## 四、行为测试：场景有意图，判断看实际事实

场景描述调用方要达到的结果；确定性检查判断对象、原请求、产物和派发次数。
二者可以是同一个测试，不必另建“意图测试引擎”。Core 的正确性不以模型评分、
自然语言成功声明、固定推理过程或私有模块结构作为判据。

| 检查 | 可观察通过条件 | 阶段 |
| --- | --- | --- |
| 基本调用 | 普通程序取得真实产物及正确原请求关联，无需模型或协议服务器 | 1 |
| 等待者分离 | A 不再等待后，B 定位同一原任务；派发次数仍为一次 | 1 |
| 顺序与并发重复 | 同身份同请求共享原受理和结果，原生派发一次 | 1 |
| 身份冲突 | 同身份不同参数拒绝，原请求不被覆盖或再次派发 | 1 |
| 对象与范围拒绝 | 直接调用检查错误对象、过期原生身份及越界目标，原生无副作用 | 1，按选定对象适用 |
| 外部变化 | 执行方在操作处判断当前条件；后续观察不补造 Core 历史 | 1，按选定对象适用 |
| 代码组合 | 两段不同任务代码复用同一能力，真实输出符合各自条件 | 1 |
| 输出与容量 | 配置边界和超限行为可验证；无无限缓存、静默截断或越界续读 | 1；持久记录在 2 |
| 受理保存失败 | 失败被返回，派发次数为零 | 各阶段按其存储保证 |
| 中断与回报丢失 | 原事实可查或明确未知，不产生额外原生派发 | 2 的重启范围 |
| 取消与释放 | 未确认不能报停止成功；资源实际寿命与释放可检查 | 选择取消时 |
| 保留与过期 | 运行中和被引用材料受保护，过期身份不悄悄重派发 | 选择持久保留时 |

使用可控制的夹具信号、进程和存储故障，在关键边界制造失败，避免按实现函数名
断言内部结构。夹具用于证明 Core 的执行事实；科学正确性需实际领域 Owner 的
真实数据和会话另行验收。记录测试中原工具版本与环境，失败后先复现，再加入
最小回归；不要通过删除失败、改变成功条件或重复运行到通过来报告修复。

具备真实 Agent 调用环境后，Agent Owner 用明确任务、真实最终状态和多个尝试
评估工具可用性、任务质量、上下文与成本。模型评价用于难以确定性判断的部分，
说明评分标准并经人工校准，不能替代去重、范围和未知表达的正确性检查。
模型升级触发该 Owner 的回归，不让 Core 基础测试依赖模型凭据或模型输出。

## 五、故障接续：逐个验证实际中断窗口

阶段 2 只补首个流程需要的持久性与重启接续。存储名、SQL 事务或协议任务状态
都不能证明跨原生副作用的原子性；所选工具怎样确认旧任务必须实测。

| 故障窗口 | 必须表达与验证的事实 |
| --- | --- |
| 受理记录无法保存 | 返回失败，不派发；读取存储失败不能解释成“从未受理” |
| 受理已保存、派发未确认 | 保留原请求和不确定范围；重启后不得因记录存在或缺少回报自动派发 |
| 派发后失去连接或 Core 中断 | 依原生身份查询旧任务；无法定位时报告未知或不可接续，不重新执行 |
| 原生已完成、回报保存失败 | 已知完成与保存失败分别表达；可取得原材料时补存，不能重算来制造回报 |
| 取消已请求、确认丢失 | 保留请求事实；观察原资源，未确认前不报告停止或释放 |
| 记录或材料过期、容量不足 | 按公开有效期、拒绝或保留识别策略处理；清理不误删运行中或被引用材料 |

单次测试记录故障位置、原请求、可确认的原生事实、派发计数、材料与观察结果。
不把多次独立实验拼成一次成功历史。只有经过对应故障实验的重启、持久化与恢复
行为才能写成已验证保证。记录损坏、查询不可用和原生不可定位各自报告，不以一个
含糊的“失败”暗示无效果，也不为表达这些事实预建全局状态机。

## 六、CI 与交付：按变更和责任边界触发

源码、契约、说明、示例和定向回归随同一变更维护，用 [README](../README.md#构建与检查)
中可复现的本地命令在临时环境独立构建和验收。用户于 2026-10-10 决定首个源码交付
暂不配置 CI，尤其不建多平台 CI；以后由用户另行选定，接入时复用同一检查。没有
运行 CI 就不报告 CI 通过，也不配置空测试来宣称已有持续集成。

| 变更 | 必要检查 | 负责边界 |
| --- | --- | --- |
| 设计或调用说明 | 本地链接、锚点、图语法与渲染；已有示例变化时执行示例 | 本仓库文档；示例以实际存在为准 |
| Core 源码或受管契约 | 独立构建、直接程序调用、相关行为与故障回归 | Core |
| 原生工具或其调用衔接 | 受影响的原生身份、效果、寿命和结果检查 | 实际执行方；所选 Core 衔接同步检查 |
| 已选协议接入 | 契约映射、认证和限额、同一受管约束不可绕过 | 接入层；不改 Core 兼容客户端 |
| Agent 模型、Skills 或调用指导 | 明确任务的结果与可用性回归，记录模型和环境版本 | Agent Owner |
| 领域或应用组合 | 真实数据、会话和产物的选定用户流程 | 领域 Owner 与应用装配 |

各层检查可在相同基础设施运行，范围与通过结论仍分开。没有实际消费者时，不为
模型更新、所有外部服务或假定协议建立 Core 的必跑矩阵。选择测试不得漏掉受影响
的契约和故障条件；测试依赖结构与触发规则随真实源码建立，不预选 CI 产品。

构建环境固定必要依赖及其身份，使用新项目和有界超时，清理自己创建的夹具资源。
检查产物记录源码与依赖身份、实际命令、环境、结果及限制；未执行、超时和跳过
分别报告。保留失败依据，避免泄露凭据与私有原始材料。Cargo 构建和测试不并行。

构建和测试只产生候选及验收依据；部署、替换运行时、安装和发布分别选定。
测试任务不持有签名或发布凭据，也不因通过而重启用户 Host 或科学会话。涉及
外部脚本或 CI 组件时固定可核对身份与最小访问；不可信提交不得继承发布权限。

## 七、必要观测：披露执行事实，诊断帮助定位

首个流程的观测从第三节必要信息开始。受管记录用于保证，诊断帮助排查；诊断
日志不是原生效果或持久受理的权威证明，日志缺失也不表示没有执行。

- 在实际边界关联原请求、执行方、原生对象及已知结果，必要时记录阶段与错误类别。
- 分别标明观察时间、已知原生时间与来源；未知值明确未知，回报保存失败不能被日志掩盖。
- 默认诊断引用受管记录，避免重复复制代码、全部参数、原始输出、凭据或私有材料。
- 原生错误保留排查所需的类别与事实；详细堆栈按实际访问和数据边界提供，不默认传播到所有客户端。
- 诊断有容量与清理约定；故障不能静默伪装成完整记录，也不为普通读取创建总账。

当实际问题需要度量时，测量 Core 拥有的延迟、运行数、失败、输出与存储占用。
令牌、模型决策和 Agent 调用轨迹归 Agent Owner；协议连接与传输归接入层；原生
资源归执行环境。共享仪表盘不改变所有权，也不取得隐藏思维链或所有外部动作。

是否导出指标、事件、日志或链路信息，按具体诊断需要选择。每项导出说明内容、
目的地、访问、保留与成本，再复用维护中的实现；首个本地流程不默认引入遥测
后端、观测 Agent 或分布式追踪。所谓审计只覆盖声明保留的受管事实，不宣称全环境
因果、完整决策链或安全认证。可复核信息与隐私范围同时成立。

## 八、持续维护：Agent 辅助，变更仍可验证

持续改进通过真实调用、失败复现、问题定位、必要契约调整和行为回归完成。
Agent 可以阅读已有材料、生成复现、补测试或提出代码与契约变更；每项变更仍需
原始需求、真实结果和确定性验收。模型生成的用例需检查是否误解需求、遗漏失败
或只重复实现；模型不能同时替代需求来源与正确性判据。

契约变化说明触发问题、改变的行为和受影响的实际消费者；选定集成时同步必要
示例、依赖与回归。模型建议不能直接改变运行中的契约、扩大权限或重放未知动作。
自动提 PR、发消息、部署、扩容、回滚和周期维护需各自已有授权与真实需求，不能
从“自我迭代”推导出来。软件版本回退也不撤销已发生的原生或科学副作用。

首版使用已授权的单用户本地范围。Core 身份、对象和范围检查、Owner 原生条件、
接入认证与实际隔离各有职责。没有默认的“每次写入再确认”，也不以允许列表或
容器产品名称代替真实边界；远程、多用户和新增隔离按选定部署验证。新机制每次
都回答它增加什么保证、谁负责、已有能力为何不足，以及如何检查失败。

## 九、交付检查与参考依据

- 调用方通过实际程序边界闭合任务；原生产物、关联和派发次数可检查。
- 必要核心信息在调用范围内可取得；缺失、未知与不能接续的部分明确说明。
- 受影响行为与故障检查通过；记录实际执行的命令、失败或未验证范围。
- 契约、说明、示例和源码一致；资源、保留、权限与进程寿命范围公开。
- 检查 diff 和仓库状态，保留无关工作；提交连贯变更，分别报告设计、实现和验证。
- Core 独立交付；相邻源码、SDK、应用锁、部署和发布仅在对应范围选定后处理。
- 任务记录与总览反映实际交付和验证；耗时注明现场或补录来源，未知时间保持未知。
