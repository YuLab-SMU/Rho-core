# Rho Core：工程进度与耗时记录规则

启用日期：2026-10-10。目的是让研究者和后续执行者查清每项工程工作做了什么、
什么时候发生、用了多久、结果是否经过验证。使用 Markdown 和 Git 维护，由实际
执行者随任务更新；这是开发文档，不增加 Core 运行时、计时服务或自动监控 Agent。

## 一、三层文档与唯一记录位置

| 文档 | 回答的问题 | 更新方式 |
| --- | --- | --- |
| [进度总览](PROGRESS.md) | 当前做到哪一步，正在做什么，下一步是什么 | 保持当前摘要，链接任务记录；历史由 Git 和任务文件保留 |
| `work/任务ID.md` | 这项工作做了什么，什么时候做，耗时和验证依据是什么 | 开始记录、必要检查点、等待或暂停、恢复及收尾时更新 |
| 本规则与模板 | 字段怎样填写，时间怎样计算，如何判断完成 | 仅在记录口径变化时修改 |

每项选定工作使用一个稳定 ID，例如 `CORE-20261010-03`，由仓库前缀、创建日期与
当日序号组成。先查看已有记录，避免重号。一次任务跨天或多次恢复仍用原 ID；
明显改变完成条件或另选责任边界时建新任务并互相链接。总览仅引用结果，不再
复制详细时间线；设计原则、需求和实现证据分别链接实际文档、源码与检查结果。

总览保持在 200 行以内，只列当前任务、近期交付与下一步。较早记录仍在 `work/`
和 Git 中，不因移出总览删除，也不建设全产品完成事项总账。已知本地证据路径
可以写为说明，但忽略目录里的缓存不是永久证明，不能让文档读取依赖这些文件。

## 二、最小字段：动作、时间、结果都有依据

| 字段 | 填写规则 |
| --- | --- |
| 任务与范围 | ID、标题、仓库、所属阶段、执行者、用户动作、完成条件 |
| 工作性质 | 明确是设计、实现、验证、集成或发布；一次任务可覆盖多项，但结论分别表达 |
| 状态 | 待开始、进行中、等待、暂停、已完成或终止；等待注明阻碍与下一步 |
| 开始与结束 | 实际记录的起点和验收截止时刻；没有来源时写未知，不拿提交时间替代 |
| 时间区间 | 工作、等待、暂停的实际起止时间，说明这段做了什么以及时间来源 |
| 实际交付 | 已完成的具体动作、产物入口与责任边界；计划不得写成完成 |
| 验证 | 实际执行的检查、结果、适用版本或文件、失败与未验证范围 |
| 耗时 | 工作跨度、已记录工作耗时、等待与暂停；计时缺口单独说明 |
| 来源与下一步 | 源变更提交、已有证据、未解决问题与继续动作 |

已完成表示该任务的完成条件已满足。例如文档任务完成不表示新运行时存在，
构建通过不表示领域集成通过，本地提交不表示已发布。无需为每次读文件、每条
命令或模型思考写一行日志；只记录实际改变进度或验证结论的检查点。

## 三、时间和耗时的统一口径

采用完整日期和带偏移量的时间，例如 `2026-10-10T02:01:13-04:00`，显示时区为
`America/New_York`。跨时区或夏令时计算先换算为 UTC，不能只相减本地钟面。
时间来源可以是执行者现场读钟、工具起止记录或明确标注的补录材料。

- **工作跨度**：记录起点到验收截止的实际时间差，包含其中等待和暂停。
- **已记录工作耗时**：工作区间的时长之和，包括阅读、设计、修改、构建与定向检查。
- **等待耗时**：无法推进该任务而等待用户、外部系统或依赖的已记录时长。
- **暂停耗时**：执行者明确停止该任务至恢复的已记录时长，不把无人继续的过夜时间算作工作。
- **未记录部分**：缺少起止时间或区间分类的部分明确写未知；不能填零或根据提交间隔猜测。

本地构建或检查正在运行且执行者仍在推进任务时计入工作区间，不再把工具耗时
叠加一次。工具耗时可以另列诊断数据，但不代表整个任务耗时或人工工时。只有
区间完整、连续且分类明确时，才验证“工作跨度＝工作＋等待＋暂停”；否则注明
哪些时间未知，仅汇总已记录部分。

同一执行者的重叠工作区间按时间并集合并。多个执行者各自记录；团队工作跨度
取最早开始至最晚结束，累计投入另算，不把并行区间简单相加当成日历耗时。
时钟倒退或来源相互冲突时保留原值、标记不能计算，核实后更正，不制造负耗时。

验收截止指主交付已完成必要检查的观察时刻。最终记录写回、记录自身的终检与
本地提交属于未计时收尾，单独说明，避免为了记下最后一秒反复追加记录。如果
收尾发现实质问题，恢复工作区间，修复后重新验收。尚在进行的任务没有结束时间，
可以用明确的统计截止报告进展，但不能伪装成最终耗时。

## 四、现场记录、补录与修正

1. **开始**：建任务记录，写目的、完成条件、当前状态和读钟时间；总览链接该任务。
2. **推进**：在有意义的产物或检查后写实际动作与依据；连续工作可以只保留一个工作区间。
3. **等待或暂停**：结束当前工作区间，记录原因及等待或暂停起点；恢复时关闭该区间并开启工作。
4. **验收**：检查实际完成条件，保留失败和未验证范围；记录观察时刻，计算能核实的区间。
5. **收尾**：更新总览和任务状态，检查记录与引用，提交连贯变更；报告交付、验证与耗时的覆盖范围。

补录历史时，Git 可以确认变更内容和提交时间；作者时间、提交时间都不自动证明
实际开始、结束或工作耗时。仅知道提交时间就保留提交时间，其余写未知。历史
报告与本地验收收据可支持对应检查结论，需标明来源和适用版本，不能声称本次重跑。

有依据的新信息可以修正当前记录，注明更正原因，Git 保留旧值。一次失败后重试
成功，两次结果都保留；未知耗时仍为未知。源变更提交可在后续更新时填写，本
记录所在提交通过 Git 查阅，不为把自身提交哈希写进自身记录而循环提交。

## 五、任务记录模板

复制以下结构到 `work/任务ID.md`，替换待填值；未开展的检查标记未执行。

```markdown
# 任务ID：任务标题

## 范围与完成条件

- 仓库、阶段、执行者：待填。
- 用户动作与完成条件：待填。
- 工作性质与保证边界：待填。
- 状态：待开始。
- 记录方式：现场记录或补录，注明来源。

## 时间与耗时

- 记录起点：未知。
- 验收截止：未结束。
- 工作跨度：未结算。
- 已记录工作耗时：未结算。
- 等待、暂停及计时缺口：待填。
- 未计时收尾：最终记录写回、终检与本地提交。

| 分类 | 开始 | 结束或统计截止 | 实际动作与时间来源 |
| --- | --- | --- | --- |
| 工作 | 待填 | 未结束 | 待填 |

## 实际交付与验证

- 实际完成：待填，链接实际产物。
- 检查及结果：未执行；执行后写实际结果和依据。
- 失败、未验证及未解决：待填。
- 源变更提交或查阅方式：待填。
- 下一步：待填。
```

不记录凭据、私有项目材料、模型隐藏思维链或与该工程任务无关的行为。记录由
实际执行者维护；此次不建立定时采集、通知、外部发布或部署。首个实现任务仍按
[工程指南](ENGINEERING.md) 选择最小受管流程，进度记录不成为运行时的新依赖。
