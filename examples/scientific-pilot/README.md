# 原生可核验的科研消费者试点

研究问题是：在预先选定的 15 株 Iris versicolor 与 15 株 Iris virginica 中，
萼片长度均值的差异，相对于固定观测值、交换物种标签的参考分布有多极端？
这里使用真实的 Iris 测量值，不生成模拟科学结果。选择每组前 15 条是为了在
有限时间内穷举全部 155,117,520 种标签分配；它是示例的固定选择规则，
不能据此声称完整数据或总体的效应，更不是随机处理的因果结论。

数据见 [`iris.csv`](iris.csv)，保留 R `datasets::iris` 的原行号 51–65、101–115、
物种与萼片长度（整数 0.1 cm）。数据来源与单位见
[R 官方 Iris 文档](https://stat.ethz.ch/R-manual/R-devel/library/datasets/html/iris.html)，
其中记录 Anderson 的采集与 Fisher 的分析。`test_science.py` 在 R 可用时直接对比
安装的 `iris` 原行号、标签与数值；运行本身只依赖 Python 标准库。

## 分析与独立判定

[`analyze.py`](analyze.py) 枚举每个大小为 15 的观测子集，用整数计算
`abs(2 * selected_sum - pooled_sum)`。组大小相等，因此该统计量与均值差的
绝对值等价。双侧 p 值包括等于观测统计量的分配，分子为更极端或相等的
分配数，分母为 `choose(30,15)`。观测值相同的不同植物仍是独立标签分配，
不会因数值重复而合并观察对象。效应另以 `virginica - versicolor` 的均值差报告。

[`verify.py`](verify.py) 不导入分析脚本；它用整数子集和动态规划计算生成函数
`product(1 + z*x^value)` 的系数，再得到完整统计分布。核验全部分布、组合总数、
尾部计数、精确分数、效应、输入原始字节摘要，以及完整结果标记。组合总数有
二项式系数 oracle，子集与补集还有对称性约束。这里核验方法的实现与固定输入上的
结论；标签可交换的假设及研究问题是否适合这种参考分布仍必须明确。

[`test_science.py`](test_science.py) 的九项检查包括一个手算的六分配例子、重复数值、
平移/正比例缩放/组标签交换，以及刻意破坏 p 值、计数、分布、完成标志与输入原始
字节的反例。输入增加空行不会改变测量值，却必须因摘要不符而拒绝。
同时检查输入大小界限，以及直接重复执行会在旧输出保护生效前记录第二次原生进入。
这些自动独立检查承担判定，人工查看报告不作为唯一正确性依据。

## 可复现运行

从仓库根目录运行，CLI 必须是已构建的当前二进制；脚本不构建 Core：

```sh
python3 examples/scientific-pilot/test_science.py -v
python3 examples/scientific-pilot/test_consumer.py -v
python3 examples/scientific-pilot/run.py --binary target/debug/rho-core \
  --root /private/tmp/rho-iris-pilot-example
```

`--root` 必须不存在，路径要足够短以容纳 Unix socket。运行先直接调用 Python
得到原生基线，再在独立新项目启动一个独立宿主，用公开 CLI 提交相同分析：

1. 观察真实枚举进度后，中断独立 `wait` 客户端；下一次 `lookup` 找回仍在执行的原 `run_id`。
2. 用逐字节相同的原请求身份重复 `submit`，得到 `existing`；继续等待与读输出，
   核验只有一次原生进入、启动标记未改变、最终产物与原生基线相同。
3. 新身份开始另一份真实计算，在计算有进度时 `cancel`；核对实际 SIGTERM、
   终态与组释放，保留部分进度，并确认没有完整推断产物。
4. 再次送达已取消的原身份，仍返回原 `run_id`，不重新运行。

脚本只停止自己启动的宿主，不使用已有项目或用户 Host。原受理、查询、重复送达、
取消与输出回复保留在 `evidence/cli-calls.json`；读输出用 offset 分段接续。
`evidence/report.json` 只在全流程完成后写入，包含两个原运行身份；出现失败保留
已有文件与 `evidence/failure.json`，不会清除失败证据或悄悄换身份重试。
原生产物在 `project/native/`、`project/managed/`、`project/cancelled/`，
最后一个只应有启动标记与部分进度。取消不回滚已经写入的进度。

输入文件由调用方复制并核验摘要，Core 保存脚本快照与原请求，**不会快照数据文件**。
这里使用独立夹具目录，防止别的流程改变输入。`launch.json` 是原生脚本的观察材料，
旁边的 `managed.launch-attempts.jsonl` 与 `cancelled.launch-attempts.jsonl` 在进入脚本时、
检查已有输出目录之前追加 PID 与时间，避免第二次进入因目录保护退出却被误计为一次。
消费者核对两者各只有一条记录。这些是进入执行的观察，受理和去重以 CLI 的原记录为
依据；不把文件标记冒充原子性的外部 exactly-once 保证。
此示例不涉及宿主崩溃后的重新持有、网络/模型或新科学 Core API。

## 资源与结果解释

原生分析默认最多 200,000,000 种分配（`--max-permutations` 可配置），超限时拒绝枚举，
保护 CPU 工作量；解析输入最多 128 KiB、32 行、测量绝对值 10,000，越界明确失败。
这些是此示例的界限，不是 Core 的全局科研限额。每 100,000 次更新一次进度
（`--progress-every` 可配置）；完整产物使用临时文件写入后原子替换。输出目录必须新建，
防止覆盖原结果。部分进度的 `complete=false` 不能作为 p 值或完整推断使用。
消费者默认单次计算 120 秒，`--timeout` 可配置为 1–600 秒；超时是失败证据，
脚本结束自己的宿主并停止其持有的计算，不自动重跑。
Python 3.14.4 的一次实测中，原生完整枚举用时约 28.99 秒，受管枚举约 34.93 秒；
实际耗时随机器与负载变化。工作脚本没有添加人工等待。`test_consumer.py` 另外检查
原生超时的部分输出与失败保留、oracle 失败保留，以及无效宿主就绪回复后的进程清理。

固定输入的精确结果是 10,196,772 / 155,117,520，即 `849731/12926460 ≈ 0.06574`；
均值差为 `73/150 ≈ 0.48667 cm`。完整参考分布说明这个 p 值从何而来，
没有 Monte Carlo 抽样误差或浮点尾部比较误差。这个值高于 0.05，
因此不能把结果写成“按 0.05 阈值已经证明差异”；也不能把阈值判断写成没有效应。
这里可准确解释的是选定 30 条观测值与声明的置换规则下的结果。

数据、数学与运行保证是三条独立证据：R 原生数据核对、独立 DP 的数值核验、
以及公开 Core CLI 的寿命/原身份/停止事实。成功的受管运行不会自动使科学结论成立。
